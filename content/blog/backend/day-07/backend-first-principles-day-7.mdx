# Handler, Service, and Repository: How a Backend Request Moves Through Clean Architecture

> *“Learning how routers, handlers, services, repositories, and databases cooperate without turning one endpoint into the entire application.”*

## The Endpoint That Tried to Do Everything

Before this lesson, I thought an endpoint was simply the place where backend work happened.

The request arrives. The route function validates it, talks to the database, and sends a response. For a tiny application, that mental model feels completely reasonable.

```ts
app.post("/users", async (req, res) => {
  // validate input
  // normalize email
  // check whether email exists
  // hash password
  // insert user
  // send welcome email
  // catch database errors
  // decide HTTP status
  // shape response
});
```

Then the comments become real code.

The route learns about HTTP status codes, request validation, business rules, password hashing, SQL or ORM operations, email delivery, database errors, and public response formatting. Every new requirement enters the same function because that function already “creates the user.”

At first, the obvious problem seems to be its length.

> **But is the function difficult because it is long, or because one function owns too many responsibilities?**

That distinction changed the lesson for me. A long function can be divided into random helpers and still have no architecture. If `createUserHelper()` still receives `req`, writes SQL, hashes a password, and chooses status `409`, I have moved code without creating a meaningful boundary.

The goal is not more files.

The goal is to make each part of the request answer a different kind of question.

That is the idea behind **separation of concerns**.

---

## 1. My Original Mental Model

My first model of backend code looked like this:

```text
Request
   ↓
Route function
   ↓
Database
   ↓
Response
```

For a small CRUD experiment, this can work. I can see the whole operation in one place, there are few files, and I can build something quickly.

The problem appears when “create a user” stops meaning only “insert one row.”

Now the application must normalize the email, protect the role, check registration policy, prevent duplicates, hash the password, write the user, perhaps publish an event, hide internal fields, and return consistent errors. Other endpoints need some of the same rules too.

Then several problems begin to repeat:

- the same business rule is copied into several handlers;
- tests need fake HTTP requests just to test email registration rules;
- SQL and ORM details leak into controllers;
- database errors become inconsistent HTTP responses;
- changing the framework affects code that should only know the business operation;
- one handler grows to hundreds of lines;
- a small persistence change risks breaking response formatting.

My improved model is:

```text
Client Request
      ↓
Router
      ↓
Handler / Controller
      ↓
Service
      ↓
Repository
      ↓
Database
```

The result travels back upward:

```text
Database Result
      ↑
Repository
      ↑
Service
      ↑
Handler
      ↑
HTTP Response
```

This does not mean every application needs one class for every arrow. These are responsibility boundaries, not laws about file counts or object-oriented programming.

A small application may keep a repository contract and implementation together. A simple read endpoint may need almost no service logic. The important question is still:

> **Which part of the system should know this fact?**

---

## 2. Separation of Concerns

The simplest definition I found is:

> **Code that changes for different reasons should not be forced to live in the same place.**

Consider what causes each part to change:

| Concern | It changes when... |
| --- | --- |
| Handler | the HTTP contract, status, header, or response shape changes |
| Service | a business rule or use-case sequence changes |
| Repository | the persistence operation, query, or record mapping changes |
| Database schema | stored-data guarantees and relationships change |

These reasons can overlap during a feature, but they are not the same responsibility.

### A Small Restaurant Analogy

I can picture the router as the person directing an order to the correct station. The handler receives and translates the customer’s order. The service decides how that order must be fulfilled. The repository communicates with the inventory records, and the database stores those records.

The analogy is useful only up to that point. Real backend layers are code boundaries, and data moves through them using explicit contracts.

### What Do We Gain?

Clear boundaries improve:

- **readability**, because each file answers fewer kinds of questions;
- **maintainability**, because a business-rule change has a natural home;
- **testability**, because the service can be tested without Express or a real database;
- **replaceable infrastructure**, because persistence details sit behind a contract;
- **consistency**, because errors and responses follow one policy;
- **reduced coupling**, because deeper code does not need to understand HTTP.

But there is a cost too:

- more files and names;
- more interfaces and handoffs;
- more decisions about where code belongs;
- a risk of creating abstractions before the application needs them.

> **Clean architecture is not about maximizing the number of layers. It is about making important boundaries explicit.**

That sentence prevents two opposite mistakes: putting everything in one route, and creating ten empty layers that only forward the same value.

## 3. The Complete Request Lifecycle

I will use one request throughout this article:

```http
POST /users
Content-Type: application/json
```

```json
{
  "name": " Belema ",
  "email": "BELEMA@EMAIL.COM",
  "password": "secret-password",
  "age": "21",
  "role": "admin"
}
```

There is already an important security problem in this body. A public registration endpoint must not let a client turn itself into an administrator. Our contract will reject the unknown `role` field instead of silently accepting it.

Here is the complete lifecycle:

```text
1. Client sends an HTTP request
2. Server parses the request
3. Router matches method and path
4. Request boundary validates and transforms input
5. Handler constructs a command and calls the service
6. Service applies business rules
7. Repository performs persistence operations
8. Database enforces stored-data constraints
9. Result moves back through the service
10. Handler maps the result to HTTP
11. Response is sent to the client
```

Data flows downward as the request becomes narrower and more trustworthy. Results flow upward as database data becomes an application result and finally a safe HTTP response.

### Parsing Is Not Validation

The handler usually does not manually decode the JSON bytes. In Express, `express.json()` normally runs first and places the parsed value on `req.body`. Malformed JSON may fail in that middleware before the route handler runs.

But successful parsing proves very little.

```text
JSON parsing:
“Can these bytes become a JavaScript value?”

Validation:
“Does that value satisfy this endpoint’s contract?”
```

`{"role":"admin"}` is valid JSON. It is not a valid public Create User command.

Day 6 was about making untrusted request data earn trust at the boundary. Day 7 begins from that boundary and asks what each part of the application should do next.

---

## 4. The Router: Choosing the Handler

Before the three main layers, the router must decide which handler receives the request.

```ts
router.post(
  "/users",
  validateBody(createUserSchema),
  userHandler.createUser,
);
```

The router matches the HTTP method and path, captures route parameters, attaches middleware, and connects the request to the final handler.

Route configuration may attach authentication, authorization, validation, rate limiting, and then the handler. That does not mean the router should implement those concerns itself.

The router should not hash a password, query the database, make registration decisions, or build a large response object. It answers one main question:

> **Where should this request go?**

After it has answered that, the handler takes over.

## 5. The Handler or Controller Layer

Different frameworks use **handler** and **controller** in slightly different ways. In this article, both mean the function that adapts HTTP to an application use case.

The handler understands `req`, `res`, and `next`. The service should not.

### What the Handler Does

A handler can:

1. receive already parsed request data;
2. read validated body, params, query, headers, and authentication context;
3. construct an explicit service command;
4. call the appropriate service operation;
5. translate the application result into an HTTP response;
6. forward expected and unexpected errors to a shared mapper.

The command for this use case is narrow:

```ts
type CreateUserCommand = {
  name: string;
  email: string;
  password: string;
  age: number | null;
};
```

Notice what is missing: `role`, `req`, `res`, headers, cookies, and database columns.

### Why Not Pass `req.body`?

This shortcut is tempting:

```ts
await userService.createUser(req.body);
```

But it allows raw external fields to leak inward. The service becomes coupled to the request shape. A field added by a frontend later may silently become writable. A privileged `role` field may reach persistence. Tests also become less explicit because nobody can see the exact input contract.

The handler should perform an allowlisted handoff:

```ts
const createUser: RequestHandler = async (req, res, next) => {
  try {
    const command: CreateUserCommand = {
      name: req.validatedBody.name,
      email: req.validatedBody.email,
      password: req.validatedBody.password,
      age: req.validatedBody.age,
    };

    const user = await userService.createUser(command);

    return res.status(201).json({
      data: presentUser(user),
    });
  } catch (error) {
    next(error);
  }
};
```

This handler is thin, but “thin” does not mean useless. It owns an important translation: HTTP input becomes an application command, and an application result becomes HTTP output.

### What the Handler Should Not Do

The handler should not contain:

- SQL or ORM queries;
- password-hashing policy;
- rules deciding which role public registration receives;
- complex workflow orchestration;
- email delivery;
- transaction management;
- database-driver error parsing;
- raw row responses that expose password hashes.

One correction was especially important for me: request validation belongs at the application boundary, but that does not mean every validation rule must be typed directly inside the handler body. A project may use middleware, schemas, DTOs, pipes, or controller helpers.

The location can vary. The boundary guarantee should not.

## 6. The Service Layer

The service is the application’s use-case and business-orchestration layer.

I used to hear “keep business logic in the service” and imagine a collection of pure functions. That is too absolute. A service may coordinate repositories, password hashers, token generators, email gateways, payment clients, clocks, transaction managers, or event publishers.

The important property is not purity.

> **The important property is that the service speaks the language of the use case instead of the language of HTTP or SQL.**

### What the Service Does

The service can:

- receive an explicit command;
- enforce business rules and current-state invariants;
- coordinate repositories and external dependencies;
- control the sequence of the use case;
- return an application result;
- throw meaningful application or domain errors.

For Create User, the service may perform this sequence:

```text
Is public registration enabled?
      ↓
Does this email already exist?
      ↓
Hash the password
      ↓
Create a normal user
      ↓
Publish or schedule “user created”
      ↓
Return the created user
```

```ts
class UserService {
  constructor(
    private readonly users: UserRepository,
    private readonly passwordHasher: PasswordHasher,
    private readonly registrationPolicy: RegistrationPolicy,
  ) {}

  async createUser(command: CreateUserCommand): Promise<User> {
    if (!this.registrationPolicy.isOpen()) {
      throw new RegistrationClosedError();
    }

    const existingUser = await this.users.findByEmail(command.email);

    if (existingUser) {
      throw new EmailAlreadyRegisteredError(command.email);
    }

    const passwordHash = await this.passwordHasher.hash(command.password);

    return this.users.create({
      name: command.name,
      email: command.email,
      passwordHash,
      age: command.age,
      role: "user",
    });
  }
}
```

The client never chooses the role. The service passes `role: "user"` because that is the registration rule.

A production system might create the user and an outbox event in one transaction, then deliver the welcome email asynchronously. That infrastructure is not required to understand the boundary, so the complete example below stays focused on the dependencies it actually defines.

### Request Validation and Business Validation

These are related, but they answer different questions.

| Request-contract validation | Business validation |
| --- | --- |
| Is `email` a string? | Is registration currently enabled? |
| Does it have an email format? | Does the email already belong to an account? |
| Can documented `"21"` become an integer? | Is this actor allowed to create this kind of user? |
| Are unknown fields rejected? | Can this entity move to the requested state? |

Services should not repeat the HTTP request-shape checks that the boundary already completed. But they absolutely must enforce business rules and current-state invariants.

The service should not access `req` or `res`, choose status codes, construct SQL, return Express responses, or expose raw database exceptions to a client.

## 7. The Repository Layer

The repository is a persistence abstraction. It translates the application’s persistence needs into database operations.

The service says, “find a user by email” or “create this user.” The repository decides how that becomes an ORM call or parameterized SQL query.

Its responsibilities may include:

- finding entities and checking existence;
- creating, updating, and deleting stored data;
- executing persistence-specific filters;
- loading related records when the contract requires them;
- mapping database rows into application objects;
- translating known driver failures into stable infrastructure errors.

### A Repository Method Is a Cohesive Operation

I originally thought every repository method had to equal exactly one SQL query. That rule is too rigid.

> **One repository method should represent one cohesive persistence operation with a stable contract.**

It may internally execute more than one query, use a transaction, load related data, or call several ORM methods. Persistence details still remain behind the same boundary.

Useful contracts look like this:

```ts
findById(id: string): Promise<User | null>
findByEmail(email: string): Promise<User | null>
existsByEmail(email: string): Promise<boolean>
create(input: NewUserRecord): Promise<User>
list(query: UserListQuery): Promise<PaginatedResult<User>>
```

Names such as `findByEmail`, `existsByEmail`, and `listByOrganization` reveal intent. Names such as `getData`, `doQuery`, `process`, and `fetchStuff` hide it.

### The SQL Idea

This portfolio does not install an application ORM or database driver directly, so the full example uses a small generic database interface. The safety principle is the same with any driver: bind input as parameters.

```ts
await db.query(
  "SELECT id, name, email FROM users WHERE email = ?",
  [email],
);
```

Never interpolate user input into SQL:

```ts
// Dangerous: do not do this.
await db.query(
  `SELECT * FROM users WHERE email = '${email}'`,
);
```

### Rows, Entities, and Public Responses

A database row may contain `password_hash`. An internal application object may also need that value during authentication. Neither fact means the public response may expose it.

The repository maps storage data to an application object. A presenter at the HTTP boundary then allowlists safe public fields.

Repositories should not access `req` or `res`, choose status codes, decide actor permissions, send email, call payment APIs, or own the registration workflow.

And a repository does not replace database integrity. The database still needs unique indexes, foreign keys, not-null constraints, and check constraints. Application boundaries improve behavior; database constraints protect stored truth.

## 8. Dependency Direction and Dependency Injection

Who knows about whom?

```text
Handler
   ↓ depends on
Service
   ↓ depends on a contract
Repository implementation
   ↓ depends on
Database driver or ORM
```

The service should preferably depend on a repository contract instead of constructing a database client itself.

```ts
const userRepository = new SqlUserRepository(db);
const passwordHasher = new BcryptPasswordHasher();
const registrationPolicy = new OpenRegistrationPolicy();

const userService = new UserService(
  userRepository,
  passwordHasher,
  registrationPolicy,
);

const userHandler = createUserHandler(userService);
```

This is manual dependency injection. No container or decorator library is required.

> **Dependency injection is not mainly about using a library. It is about giving an object its dependencies instead of letting it secretly create them.**

In a service test, I can give `UserService` an in-memory repository and fake password hasher. The service never notices because it depends on behavior, not construction details.

## 9. One Complete TypeScript Example

This section connects the boundaries into one implementation. It is a conceptual TypeScript, Express, and Zod 4 example because this portfolio is a Next.js content application and has no direct backend framework, ORM, or database dependency.

A possible structure is:

```text
src/
  users/
    user.routes.ts
    user.schema.ts
    user.handler.ts
    user.service.ts
    user.repository.ts
    user.errors.ts
    user.presenter.ts
    user.types.ts
  error-handler.ts
  composition-root.ts
```

This is not the only valid structure. A smaller application may group some of these files together.

### `user.types.ts` — Contracts Between the Layers

```ts
export type CreateUserCommand = {

  email: string;

};

export type NewUserRecord = {

};

export type User = {
  id: string;
  name: string;
  email: string;
  passwordHash: string;
  age: number | null;
  role: "user" | "admin";
  createdAt: Date;
};

  name: string;
  email: string;
  age: number | null;
```

### `user.schema.ts` — Reject and Transform the Request

```ts
import { z } from "zod";

const ageFromRequest = z
  .union([z.string(), z.number(), z.null()])
  .transform((value, context) => {
    if (value === null) return null;

    const age =
      typeof value === "number"
        ? value
        : /^\d+$/.test(value)
          ? Number(value)
          : Number.NaN;

    if (!Number.isSafeInteger(age)) {
      context.addIssue({
        code: "custom",
        message: "Age must be a whole number.",
      });
      return z.NEVER;
    }

    return age;
  })
  .pipe(z.number().int().min(13).max(150).nullable());

export const createUserSchema = z.strictObject({
  name: z.string().trim().min(1).max(80),
  email: z.string().trim().toLowerCase().pipe(z.email().max(254)),
  password: z.string().min(12).max(128),
  age: ageFromRequest.optional().default(null),
});
```

Because the object is strict, the original request fails at the boundary:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid fields.",
    "fields": [
      {
        "field": "body",
        "message": "Unrecognized key: role"
      }
    ]
  }
}
```

The service is never called. If the client removes `role` and resends, the schema produces:

```ts
{
  name: "Belema",
  email: "belema@email.com",
  password: "secret-password",
  age: 21,
}
```

### `user.routes.ts` — Match and Validate

```ts
router.post(
  "/users",
  validateBody(createUserSchema),
  userHandler.createUser,
);
```

`validateBody` parses `req.body`, returns a `400` validation response on failure, and attaches only the parsed output as `req.validatedBody` on success.

### `user.handler.ts` — Translate HTTP to the Use Case

```ts
import type { RequestHandler } from "express";

export function createUserHandler(userService: UserService) {
  const createUser: RequestHandler = async (req, res, next) => {
    try {
      const command: CreateUserCommand = {
        name: req.validatedBody.name,
        email: req.validatedBody.email,
        password: req.validatedBody.password,
        age: req.validatedBody.age,
      };

      const user = await userService.createUser(command);

      return res.status(201).json({
        data: presentUser(user),
      });
    } catch (error) {
      next(error);
    }
  };

  return { createUser };
}
```

### `user.errors.ts` — Stable Error Meaning

```ts
export class EmailAlreadyRegisteredError extends Error {
  readonly code = "EMAIL_ALREADY_REGISTERED";

  constructor(readonly email: string) {
    super("The email is already registered.");
  }
}

export class RegistrationClosedError extends Error {
  readonly code = "REGISTRATION_CLOSED";
}

export class UniqueEmailConstraintError extends Error {
  readonly code = "UNIQUE_EMAIL_CONSTRAINT";
}
```

### `user.repository.ts` — Persistence Contract and Implementation

```ts
export interface UserRepository {
  findByEmail(email: string): Promise<User | null>;
  create(input: NewUserRecord): Promise<User>;
}

type UserRow = {
  id: string;
  name: string;
  email: string;
  password_hash: string;
  age: number | null;
  role: "user" | "admin";
  created_at: Date;
};

type Database = {
  query<T>(sql: string, values: readonly unknown[]): Promise<T[]>;
};

function mapUserRow(row: UserRow): User {
  return {
    id: row.id,
    name: row.name,
    email: row.email,
    passwordHash: row.password_hash,
    age: row.age,
    role: row.role,
    createdAt: row.created_at,
  };
}

export class SqlUserRepository implements UserRepository {
  constructor(private readonly db: Database) {}

  async findByEmail(email: string): Promise<User | null> {
    const rows = await this.db.query<UserRow>(
      `SELECT id, name, email, password_hash, age, role, created_at
       FROM users
       WHERE email = ?
       LIMIT 1`,
      [email],
    );

    return rows[0] ? mapUserRow(rows[0]) : null;
  }

  async create(input: NewUserRecord): Promise<User> {
    try {
      const rows = await this.db.query<UserRow>(
        `INSERT INTO users (name, email, password_hash, age, role)
         VALUES (?, ?, ?, ?, ?)
         RETURNING id, name, email, password_hash, age, role, created_at`,
        [
          input.name,
          input.email,
          input.passwordHash,
          input.age,
          input.role,
        ],
      );

      return mapUserRow(rows[0]);
    } catch (error) {
      if (isUniqueEmailViolation(error)) {
        throw new UniqueEmailConstraintError();
      }

      throw error;
    }
  }
}
```

The `Database` interface is intentionally generic. Real placeholder syntax and `RETURNING` support depend on the chosen driver and database. The important points are explicit columns, bound parameters, stable return values, and translated known errors.

### `user.service.ts` — Enforce and Orchestrate

```ts
export interface PasswordHasher {
  hash(plainText: string): Promise<string>;
}

export interface RegistrationPolicy {
  isOpen(): boolean;
}

export class UserService {
  constructor(
    private readonly users: UserRepository,
    private readonly passwordHasher: PasswordHasher,
    private readonly registrationPolicy: RegistrationPolicy,
  ) {}

  async createUser(command: CreateUserCommand): Promise<User> {
    if (!this.registrationPolicy.isOpen()) {
      throw new RegistrationClosedError();
    }

    const existingUser = await this.users.findByEmail(command.email);

    if (existingUser) {
      throw new EmailAlreadyRegisteredError(command.email);
    }

    const passwordHash = await this.passwordHasher.hash(command.password);

    try {
      return await this.users.create({
        name: command.name,
        email: command.email,
        passwordHash,
        age: command.age,
        role: "user",
      });
    } catch (error) {
      if (error instanceof UniqueEmailConstraintError) {
        throw new EmailAlreadyRegisteredError(command.email);
      }

      throw error;
    }
  }
}
```

### `user.presenter.ts` — Allowlist the Response

```ts
export function presentUser(user: User): PublicUser {
  return {
    id: user.id,
    name: user.name,
    email: user.email,
    age: user.age,
    role: user.role,
    createdAt: user.createdAt.toISOString(),
  };
}
```

The presenter has no `password` or `passwordHash` property to return.

### `error-handler.ts` — Map Meaning to HTTP

```ts
import type { ErrorRequestHandler } from "express";

export const errorHandler: ErrorRequestHandler = (
  error,
  req,
  res,
  _next,
) => {
  if (error instanceof EmailAlreadyRegisteredError) {
    return res.status(409).json({
      error: {
        code: error.code,
        message: "An account already uses this email.",
      },
    });
  }

  if (error instanceof RegistrationClosedError) {
    return res.status(403).json({
      error: {
        code: error.code,
        message: "Public registration is currently unavailable.",
      },
    });
  }

  req.log.error(
    { error, requestId: req.id },
    "Unhandled request error",
  );

  return res.status(500).json({
    error: {
      code: "INTERNAL_SERVER_ERROR",
      message: "Something went wrong.",
      requestId: req.id,
    },
  });
};
```

### `composition-root.ts` — Connect the Real Dependencies

```ts
const users = new SqlUserRepository(db);
const passwordHasher = new BcryptPasswordHasher();
const registrationPolicy = new OpenRegistrationPolicy();

const userService = new UserService(
  users,
  passwordHasher,
  registrationPolicy,
);

export const userHandler = createUserHandler(userService);
```

Now I can read the entire flow without one file owning every detail:

```text
POST /users
      ↓
strict schema rejects role and transforms age
      ↓
handler creates CreateUserCommand
      ↓
service enforces registration and uniqueness rules
      ↓
repository persists explicit fields
      ↓
database enforces unique email
      ↓
service returns the created entity
      ↓
handler presents safe JSON with 201 Created
```

## 10. Error Handling Across the Layers

Errors made this architecture finally click for me, because each layer knows different information.

The request boundary understands request format. The service understands business meaning. The repository understands storage failures. The HTTP boundary understands status codes.

### The Errors Each Layer Can Recognize

| Layer | Examples |
| --- | --- |
| Request boundary | malformed JSON, invalid fields, unsupported media type |
| Service | duplicate registration, forbidden operation, invalid state transition, missing resource |
| Repository / infrastructure | unique violation, connection failure, timeout, deadlock |
| Handler / error middleware | mapping known application meaning to HTTP |

The service can throw `EmailAlreadyRegisteredError`. It should not throw “409 Conflict,” because `409` is an HTTP decision. The same service might later be called by a job or command-line program where HTTP does not exist.

Stable types or codes are safer than message comparison.

```ts
// Fragile: wording is not a contract.
if (error.message === "Email already taken") {
  // ...
}
```

```ts
// Stable application meaning.
if (error instanceof EmailAlreadyRegisteredError) {
  // ...
}
```

### Common HTTP Mappings

- malformed request: `400 Bad Request`;
- authentication failure: `401 Unauthorized`;
- authenticated but forbidden: `403 Forbidden`;
- missing resource: `404 Not Found`;
- duplicate email or state conflict: `409 Conflict`;
- valid structure but unacceptable semantics, if the API uses this convention: `422 Unprocessable Content`;
- unexpected failure: `500 Internal Server Error`.

The exact choice between `400` and `422` varies across APIs. Consistency inside one API is more valuable than pretending one convention is universally mandatory.

### Expected and Unexpected Failures

Expected failures should be translated predictably. Unexpected failures should be logged with useful internal context and returned as a generic response.

The client must not receive SQL text, driver details, stack traces, passwords, tokens, or internal configuration. A request ID is safe and useful because it lets the team connect the public failure to internal logs.

Centralized Express error middleware also prevents every handler from copying a large `try/catch` decision tree. Handlers can forward errors; one place applies the HTTP policy.

---

## 11. The Database Race Condition

The service checks whether an email already exists. That produces a friendly error in the normal case, but it cannot guarantee uniqueness under concurrency.

```text
Request A checks email → available
Request B checks email → available
Request A inserts the email
Request B inserts the same email
```

Both checks were truthful when they ran. Without a database constraint, both inserts may succeed.

The database therefore needs a unique constraint:

```sql
CREATE UNIQUE INDEX users_email_unique
ON users (email);
```

Now one insert succeeds and the other receives a unique-constraint violation. The repository recognizes that database-specific failure and throws `UniqueEmailConstraintError`. The service translates it into `EmailAlreadyRegisteredError`. The HTTP error middleware returns `409 Conflict`.

```text
Database-specific unique violation
      ↓
Repository infrastructure error
      ↓
Service application conflict
      ↓
HTTP 409 response
```

This is defense in depth:

- the service check gives a fast, understandable normal path;
- the database constraint provides the real concurrency guarantee;
- error translation keeps database details out of HTTP.

The repository does not replace the database. The service does not replace the database. Each layer protects what it is capable of knowing.

---

## 12. Testing the Boundaries

The architecture adds the most value when I can test each responsibility without rebuilding the entire world.

### Handler Test

Give the handler validated request data and a fake service. Verify that it constructs the correct command and returns `201` with safe JSON. The test does not need a real database.

### Service Test

Give the service an in-memory repository, fake hasher, and controllable registration policy.

Test questions such as:

- Does an existing email produce `EmailAlreadyRegisteredError`?
- Is the password hasher called with the plain password?
- Does persistence receive a hash instead of the plain password?
- Is the assigned role always `user`?
- Does closed registration stop before hashing and persistence?
- Does a unique-constraint race become the same application conflict?

No Express request or response object is required.

### Repository Integration Test

Use a real test database to verify queries, row mapping, parameter binding, null handling, and constraint translation.

This is where separation of concerns becomes practical rather than decorative. A failure tells me which boundary is broken.

## 13. A Smaller Read Flow

Not every endpoint needs the same amount of orchestration. A simple read may look like this:

```text
GET /users/:id
      ↓
Router matches and validates id
      ↓
Handler calls getUser(id)
      ↓
Service requests repository.findById(id)
      ↓
Service throws UserNotFoundError or returns user
      ↓
Handler presents safe user JSON
```

The service may be very small, and that is fine. The boundary still gives the application one place for future visibility, permission, or state rules.

But if an application is truly tiny and no business distinction exists, adding forwarding layers only to satisfy a diagram may be overengineering. Architecture should serve the behavior.

## 14. Common Mistakes I Now Notice

### Mistake 1: A Thin Handler and a Giant Service

Moving every line from a controller into one enormous service only moves the problem. A service can also own too many use cases and responsibilities.

### Mistake 2: Repositories That Contain Business Policy

`createAdminIfActorCanPromote()` is not only a persistence operation. Permission and promotion rules belong in the use-case layer.

### Mistake 3: Services That Return HTTP Responses

A service returning `res.status(409)` cannot be reused outside Express and cannot be tested without HTTP machinery.

### Mistake 4: Passing Raw Bodies Downward

`req.body` is an external transport shape, not an application command. Explicit mapping protects the inner layers from mass assignment and accidental contract growth.

### Mistake 5: Trusting the Pre-Insert Check

`findByEmail()` followed by `create()` still has a race. The unique database constraint is mandatory.

### Mistake 6: Returning the ORM Row

Raw records may contain `password_hash`, internal flags, tokens, or fields the API never promised. A presenter should allowlist public fields.

### Mistake 7: Creating Layers With No Boundary

If every method accepts `any`, passes the same raw object, and leaks driver errors upward, the folders look clean while the responsibilities remain mixed.

## 15. My Final Mental Model

At the beginning, I saw this:

```text
Request → Route → Database → Response
```

Now I see a series of translations and decisions:

```text
External HTTP request
      ↓
Router chooses the operation
      ↓
Request boundary earns a trustworthy shape
      ↓
Handler translates HTTP data into a command
      ↓
Service enforces the use case and business rules
      ↓
Repository translates persistence intent
      ↓
Database protects stored truth
      ↑
Repository returns an application object
      ↑
Service returns the use-case result
      ↑
Handler presents safe HTTP JSON
```

The biggest realization for me was that the layers are not mainly about folders.

They are about knowledge.

- The router knows **where** the request goes.
- The request boundary knows **whether external data matches the contract**.
- The handler knows **HTTP**.
- The service knows **the use case and business rules**.
- The repository knows **how persistence works**.
- The database knows **what stored states are allowed**.

When one layer starts knowing everything, changes become dangerous. When every layer knows only what it needs, the complete request becomes easier to follow even though it passes through more than one file.

That sounds like a contradiction: more pieces, but a clearer picture.

Now I understand why. Each piece has a name, a contract, and a reason to change.

## Checkpoint Questions

### 1. Why is splitting a long route into helpers not automatically clean architecture?

Because the helpers may still mix HTTP, business rules, persistence, and error mapping. A boundary is defined by responsibility and contract, not file count.

### 2. Why should the handler create an explicit command?

It prevents raw external fields from leaking inward, makes writable fields visible, protects against mass assignment, and gives the service a framework-independent input.

### 3. Does the service assume everything is valid?

It can trust the request shape produced by the boundary, but it must still enforce business rules and current-state invariants.

### 4. Must one repository method equal one query?

No. It should represent one cohesive persistence operation with a stable contract. Its implementation may use multiple queries or a transaction.

### 5. Why check email availability if the database has a unique index?

The check improves the normal user-facing path. The unique index provides the final guarantee when concurrent requests race.

### 6. Which layer chooses `409 Conflict`?

The HTTP boundary or centralized error middleware. The service expresses an application conflict without depending on HTTP.

### 7. Why use dependency injection?

It makes dependencies explicit and replaceable. The service can receive a fake repository in tests instead of secretly constructing a real database client.

### 8. Is this folder structure mandatory?

No. Small applications may combine files. The important boundaries are the responsibilities and contracts, not the exact directory tree.

## Final Summary

One `POST /users` request taught me much more than how to insert a row.

The router chooses the handler. The request boundary parses the endpoint contract and rejects the attempted `role: "admin"`. The handler builds a narrow command. The service applies registration rules, checks email availability, hashes the password, and assigns the safe `user` role. The repository turns persistence intent into parameterized database work. The database enforces uniqueness under concurrency. Then the result moves upward and becomes a safe `201 Created` response without a password hash.

Errors follow the same boundaries in reverse. Database-specific failures become stable infrastructure meaning. The service expresses application meaning. The HTTP boundary chooses a consistent public status and message.

Before this lesson, I thought architecture meant making a project look organized.

Now I understand it as something more useful:

> **Architecture makes it clear which code is allowed to know what—and where each decision belongs.**

That changed the way I see backend code. A request is not handled by one magical function. It is carried through a set of deliberate boundaries, and every boundary makes the next part safer and easier to understand.
