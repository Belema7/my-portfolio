# Backend from First Principles — Day 5 (Part 3)

# Sessions, JWTs, and Cookies: The Core Auth Vocabulary

> *"Authentication does not end after login. Once the server knows who I am, it needs a way to remember that identity on later requests. Sessions, JWTs, and cookies are three of the most important tools in that conversation."*

---

## Introduction

HTTP is stateless.

That means each request is independent by default.

If I log in on one request, the next request does not automatically remember me unless the application creates a mechanism for that.

This is where sessions, JWTs, and cookies become important.

They are related, but they are not the same thing.

I needed to separate them clearly:

```text
Session = server-side authenticated state
JWT = signed token containing claims
Cookie = browser storage and transport mechanism
```

Once I saw that separation, the whole topic became less confusing.

### The Beginner Problem: Login Is Not Enough

When I first think about login, it feels like a single event:

```text
User enters email and password.
Server says yes.
User is logged in.
```

But HTTP does not remember that by itself.

If the browser sends another request one second later, that request is separate.

The backend needs some way to connect the second request to the successful login.

That is the job of sessions, tokens, and cookies.

They answer:

```text
How does the server recognize this user again on the next request?
```

Without one of these mechanisms, the user would have to send their password on every single request, which would be both annoying and unsafe.

---

## Topic 3.1 — Sessions

A session is server-side state that remembers an authenticated user.

The basic flow looks like this:

1. User logs in.
2. Server validates the credentials.
3. Server creates a session record.
4. Server sends the browser a session ID.
5. Browser sends that session ID on later requests.
6. Server looks up the session and identifies the user.

The session data usually lives on the server.

It may be stored in memory, a database, or a shared cache like Redis.

### Example Flow

```text
POST /login
→ Server creates session: abc123
→ Server stores: abc123 = user 15
→ Browser receives cookie: sessionId=abc123
→ Browser sends cookie on future requests
→ Server looks up abc123 and finds user 15
```

The browser does not need to know the user's role, email, or permissions.

It only holds the session ID.

The server holds the meaning.

### Session Tradeoffs

| Aspect | Session-based auth |
| --- | --- |
| State | Stateful |
| Storage | Server stores session data |
| Invalidation | Easy and immediate |
| Scaling | Needs shared session storage |
| Common use | Traditional web apps |

The biggest advantage is control.

If the user logs out or the account is disabled, the server can delete the session.

The biggest cost is state.

If the application has many servers, they must all be able to read the session.

### A More Detailed Session Example

Imagine I log in successfully.

The server creates a session record like this:

```json
{
  "sessionId": "abc123",
  "userId": 15,
  "createdAt": "2026-07-30T10:00:00.000Z",
  "expiresAt": "2026-07-30T12:00:00.000Z"
}
```

The browser does not receive all of this information.

It receives only the session ID:

```http
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax
```

On the next request, the browser sends:

```http
Cookie: sessionId=abc123
```

Then the server looks up `abc123`.

If the session exists and has not expired, the server knows the request belongs to user 15.

This is why sessions are called stateful.

The important state lives on the server.

## Topic 3.2 — JWTs

JWT stands for JSON Web Token.

A JWT is a compact signed token that can carry claims about a user.

It has three parts:

```text
header.payload.signature
```

The payload may contain claims like:

```json
{
  "sub": "15",
  "role": "ADMIN",
  "permissions": ["user:read", "user:delete"],
  "exp": 1785412800
}
```

The signature lets the server verify that the token was created by a trusted issuer and was not changed.

### JWT Flow

1. User logs in.
2. Server validates credentials.
3. Server signs a JWT.
4. Client stores the JWT.
5. Client sends the JWT on later requests.
6. Server verifies the signature and expiry.
7. Server reads the claims.

The key idea is that the server may not need to store a session record.

The token carries the data needed to identify the user.

### JWT Tradeoffs

| Aspect | JWT-based auth |
| --- | --- |
| State | Often stateless |
| Storage | Client stores token |
| Invalidation | Hard until token expires |
| Scaling | Easy across many servers |
| Common use | APIs, SPAs, mobile apps, microservices |

JWTs are powerful, but they are not magic.

The server must still validate the signature, expiry, issuer, audience, and expected claims.

A JWT should be trusted only after verification.

### What "Signed" Means for a Beginner

A JWT payload is not automatically secret.

In many JWTs, the payload is only Base64URL-encoded.

That means it can often be decoded and read.

The security comes from the signature.

The signature lets the server detect whether the token was changed.

Example:

```text
Original token says: role = USER
Attacker changes it to: role = ADMIN
Signature no longer matches
Server rejects token
```

So a JWT is not mainly a way to hide data.

It is mainly a way to carry claims in a tamper-detectable token.

Sensitive secrets should not be placed inside a JWT payload unless encryption or another protection is being used.

### Why Expiry Matters

Because JWTs are often stateless, the server may not store a session that can be deleted immediately.

If a token is stolen, the attacker may use it until it expires.

That is why access tokens should usually be short-lived.

Short expiry is a safety limit.

## Topic 3.3 — Cookies

A cookie is a small piece of data that a server can ask the browser to store.

The server sends it with `Set-Cookie`:

```http
HTTP/1.1 200 OK
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax
```

Then the browser automatically sends it back:

```http
GET /dashboard HTTP/1.1
Cookie: sessionId=abc123
```

Cookies are not authentication by themselves.

They are a transport and storage mechanism.

A cookie can carry a session ID.

A cookie can also carry a JWT.

### Important Cookie Attributes

| Attribute | Why it matters |
| --- | --- |
| `HttpOnly` | JavaScript cannot read the cookie, reducing XSS token theft |
| `Secure` | Browser only sends the cookie over HTTPS |
| `SameSite` | Helps reduce CSRF risk |
| `Max-Age` | Controls how long the cookie should live |
| `Path` | Limits where the cookie is sent |

For browser-based auth, `HttpOnly`, `Secure`, and `SameSite` are especially important.

### Cookies Are Automatic

One detail that makes cookies special is that the browser sends matching cookies automatically.

If the cookie belongs to `example.com`, then requests to `example.com` can include it without manually adding an `Authorization` header.

This is convenient for web apps.

But automatic sending also means I need to think about CSRF protection.

`SameSite` helps reduce that risk by controlling when cookies are sent on cross-site requests.

For beginners, the simple version is:

```text
Cookies are convenient because browsers manage them.
Cookies need careful settings because browsers send them automatically.
```

## Topic 3.4 — How They Work Together

The confusing part is that sessions, JWTs, and cookies can be combined.

| Combination | Meaning | Common use |
| --- | --- | --- |
| Session + Cookie | Cookie stores session ID | Traditional web apps |
| JWT + Cookie | Cookie stores signed token | Browser apps with secure cookies |
| JWT + Authorization Header | Header carries bearer token | APIs, mobile apps, service calls |

The cookie is not the same as the session.

The cookie may only carry the session ID.

The server-side session is the data the server looks up.

Similarly, a JWT is not the same as a cookie.

A JWT can be stored in a cookie, sent in an `Authorization` header, or used in other controlled environments.

### Common Beginner Confusions

**Confusion 1: "Cookie auth and session auth are the same thing."**

Not exactly.

The cookie may only store a session ID.

The session is the server-side record.

**Confusion 2: "JWT means no cookies."**

Not necessarily.

A JWT can be stored in an `HttpOnly` cookie.

**Confusion 3: "JWT means secure."**

Not automatically.

A JWT must be signed correctly, verified correctly, stored safely, and expired appropriately.

**Confusion 4: "Stateless means the server does no work."**

No.

The server still verifies the token and checks authorization rules.

## Topic 3.5 — Stateful vs Stateless

Stateful authentication means the server stores login state.

```text
Client sends session ID
Server looks up session data
```

Stateless authentication means the server does not need a session lookup for every request.

```text
Client sends signed token
Server verifies token
```

### Comparison

| Aspect | Session + Cookie | JWT + Cookie | JWT + Header |
| --- | --- | --- | --- |
| State | Stateful | Usually stateless | Usually stateless |
| Main storage | Server session store | Client cookie | Client app storage |
| Browser auto-sends | Yes | Yes | No |
| XSS token theft risk | Lower with `HttpOnly` | Lower with `HttpOnly` | Higher if stored in `localStorage` |
| CSRF concern | Needs protection | Needs `SameSite` or CSRF strategy | Lower for manual headers |
| Invalidation | Easy | Harder | Harder |
| Scaling | Needs shared store | Easier | Easier |

This table helped me understand that there is no perfect option.

Every auth mechanism has tradeoffs.

---

## Topic 3.6 — Token Storage Matters

Where a token is stored is a security decision.

Storing JWTs in `localStorage` is risky because JavaScript can read them.

If an XSS vulnerability exists, malicious JavaScript may steal the token.

For browser apps, a safer common pattern is an `HttpOnly`, `Secure`, `SameSite` cookie.

```http
Set-Cookie: accessToken=...; HttpOnly; Secure; SameSite=Lax
```

This does not remove every risk, but it reduces one major risk: direct token theft through JavaScript.

Security is always about layers.

## My Biggest Realization

I used to mix these words together.

Now I see the roles:

```text
Sessions remember auth state on the server.
JWTs carry signed claims.
Cookies store and send browser data automatically.
```

They can work together, but they solve different parts of the problem.

That distinction matters because choosing an auth strategy is really choosing a set of tradeoffs.

## Part 3 Complete!

## Final Summary

**1. Sessions are server-side state**

The client usually holds only a session ID while the server stores the meaning.

**2. JWTs are signed tokens**

They can carry identity and claims, but they must be verified on every request.

**3. Cookies are transport and storage**

They let browsers automatically send data back to the server.

**4. Stateful and stateless auth have tradeoffs**

Sessions are easier to invalidate. JWTs are easier to scale.

**5. Secure storage matters**

For browser apps, `HttpOnly`, `Secure`, and `SameSite` cookies reduce important risks.

### Checkpoint Questions

**What is a session?**

Server-side state that tracks an authenticated user's session.

**What is a JWT?**

A signed token with a `header.payload.signature` structure that can carry claims.

**What is a cookie?**

A browser mechanism for storing small data and sending it automatically with requests.

**Why is `HttpOnly` important?**

It prevents browser JavaScript from reading the cookie directly.
