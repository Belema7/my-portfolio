# Backend from First Principles — Day 5 (Part 5)

# Authorization: What Can You Do?

> *"Authentication gives the request an identity. Authorization decides what that identity is allowed to do. A secure API needs both."*

---

## Introduction

Authentication answers:

```text
Who are you?
```

Authorization answers:

```text
What can you do?
```

This distinction matters because a logged-in user should not automatically have full access to the system.

A normal user may view their own profile.

An admin may manage users.

A manager may view team reports.

A support agent may reset passwords but not view payment details.

Authorization is the system that turns identity into decisions.

### Beginner Mental Model

Imagine authentication gives the backend a name tag:

```text
This is User 15.
```

Authorization then reads the rules:

```text
User 15 can read their own profile.
User 15 cannot delete another user.
User 15 can edit posts they created.
User 15 cannot open the admin dashboard.
```

That is the important shift.

The backend is no longer dealing with an unknown request.

It is dealing with a known identity and a specific action.

Authorization is the decision-making layer between those two things.

---

## Topic 5.1 — The Core Components

Authorization decisions usually involve a few core pieces.

| Component | Meaning | Example |
| --- | --- | --- |
| Subject | Who is making the request | `User: Belema` |
| Resource | What is being accessed | `Document: report.pdf` |
| Action | What the subject wants to do | `read`, `write`, `delete` |
| Permission | A named ability | `document:read` |
| Role | A collection of permissions | `ADMIN`, `USER` |
| Policy | A rule that decides access | "Managers can view team reports" |

An authorization check usually asks:

```text
Can this subject perform this action on this resource?
```

Example:

```text
Can user 15 delete user 29?
Can user 15 read invoice 44?
Can manager 7 update project 12?
```

This makes authorization more concrete.

It is not a vague security layer. It is a decision system.

### Breaking Down One Request

Take this request:

```http
DELETE /api/projects/42
Authorization: Bearer valid-token
```

The authorization pieces are:

| Component | In this request |
| --- | --- |
| Subject | The authenticated user from the token |
| Resource | Project `42` |
| Action | Delete |
| Permission | Maybe `project:delete` |
| Policy | "Only project owners or admins can delete projects" |

The backend should not only ask:

```text
Is the user logged in?
```

It should ask:

```text
Is this logged-in user allowed to delete this exact project?
```

That is much more precise.

## Topic 5.2 — Role-Based Access Control

Role-Based Access Control, or RBAC, assigns permissions to roles, then assigns roles to users.

The flow is:

```text
Define permissions
→ Group permissions into roles
→ Assign roles to users
→ Check role or permission during requests
```

### Example

| User | Role | Permissions |
| --- | --- | --- |
| Alice | Admin | `user:read`, `user:write`, `user:delete` |
| Bob | Manager | `user:read`, `user:write` |
| Charlie | User | `user:read` for own profile |

RBAC is popular because it is easy to understand.

Most applications can start with roles like:

```text
ADMIN
MANAGER
USER
GUEST
```

### RBAC Pros and Cons

| Pros | Cons |
| --- | --- |
| Simple mental model | Can become rigid |
| Easy to manage at first | Role explosion in complex systems |
| Works for most apps | Does not capture every context |
| Easy to explain to teams | May need custom rules later |

RBAC is a strong default for many applications.

But it can become messy when every small exception becomes a new role.

### Role Explosion Explained

Role explosion happens when the app creates too many roles to handle every special case.

At first, roles may be simple:

```text
ADMIN
MANAGER
USER
```

Then requirements grow:

```text
SALES_MANAGER
SUPPORT_MANAGER
READ_ONLY_ADMIN
BILLING_ADMIN
PROJECT_ADMIN
PROJECT_EDITOR
PROJECT_VIEWER
REGIONAL_MANAGER
TEMPORARY_MANAGER
```

The role list becomes hard to understand.

At that point, permission-based checks or ABAC-style policies may become cleaner.

The beginner lesson is:

```text
Roles are useful groups, but they should not become the only way to express every rule.
```

## Topic 5.3 — Attribute-Based Access Control

Attribute-Based Access Control, or ABAC, makes decisions using attributes.

Attributes can belong to:

| Attribute source | Examples |
| --- | --- |
| User | department, clearance, location |
| Resource | owner, sensitivity, project |
| Environment | time, IP address, device |
| Action | read, write, approve, delete |

Example policies:

```text
Allow if user.department == resource.department.
Allow if user.clearance >= resource.sensitivity.
Allow if request.time is between 9 AM and 5 PM.
Allow if user.id == resource.ownerId.
```

ABAC is more flexible than RBAC.

It can express detailed rules.

But that flexibility has a cost.

### ABAC Pros and Cons

| Pros | Cons |
| --- | --- |
| Very flexible | More complex to implement |
| Fine-grained control | Policies can be hard to debug |
| Good for large organizations | Requires reliable attributes |
| Handles context well | Harder to explain than roles |

ABAC is useful in domains like healthcare, finance, government, and enterprise software where access depends on context.

### ABAC Example in Plain Language

Imagine a hospital system.

A doctor should not automatically see every patient's record.

The decision may depend on attributes:

```text
Doctor department
Patient department
Doctor assigned patients
Emergency status
Time of access
Location of request
```

An ABAC-style rule might be:

```text
Allow if the doctor is assigned to the patient,
or if emergency access is active,
and log every access.
```

This is more detailed than a simple role check.

The role `DOCTOR` is not enough.

The system needs context.

## Topic 5.4 — Claims-Based Authorization

Claims-based authorization uses claims attached to an identity.

A claim is a statement about a user or client.

Example JWT payload:

```json
{
  "sub": "15",
  "role": "ADMIN",
  "permissions": ["user:read", "user:delete"],
  "department": "engineering"
}
```

The backend can use those claims to make decisions:

```text
Does the token include role ADMIN?
Does the token include permission user:delete?
Does the department claim match the resource department?
```

Claims are useful because they can reduce database lookups.

But they can also become stale.

If a user's permissions change, an existing token may still contain old claims until it expires.

That is why short-lived access tokens matter.

### Claims Are Convenient, But Not Always Fresh

Suppose the token says:

```json
{
  "sub": "15",
  "role": "ADMIN"
}
```

Then the user is demoted from admin to normal user in the database.

If the existing token still says `ADMIN`, the backend has a problem until that token expires or is revoked.

This is the freshness tradeoff.

Claims can reduce database lookups, but they can become outdated.

Common ways to reduce the risk include:

| Strategy | How it helps |
| --- | --- |
| Short access token lifetime | Old claims expire quickly |
| Refresh token checks | Server can re-check user status |
| Token version field | Invalidate old tokens after changes |
| Permission lookup for sensitive actions | Confirm critical access from database |

For beginner projects, the main lesson is:

```text
Do not put long-lived powerful permissions in tokens without thinking about revocation.
```

## Topic 5.5 — Access Control Lists

An Access Control List, or ACL, stores access rules on the resource itself.

Example:

| Resource | User | Allowed actions |
| --- | --- | --- |
| `report.pdf` | Alice | `read`, `write` |
| `report.pdf` | Bob | `read` |
| `report.pdf` | Charlie | none |

This is common in file systems and shared drives.

The resource knows who can access it.

ACLs are very fine-grained, but they can be difficult to manage at scale.

If every document has its own list, auditing and updating permissions can become complicated.

### ACLs in a Shared Document App

Imagine a document called `roadmap.md`.

Its ACL might look like:

| Identity | Permission |
| --- | --- |
| Alice | Owner |
| Bob | Editor |
| Charlie | Viewer |
| Dana | No access |

When Bob sends:

```http
PATCH /api/documents/roadmap
```

the backend checks the document's ACL.

Bob is an editor, so the update is allowed.

When Charlie sends the same request, the backend denies it because Charlie can only view.

This model is easy to understand for shared resources.

It becomes harder when there are millions of resources and many changing permissions.

## Topic 5.6 — Principle of Least Privilege

The Principle of Least Privilege says:

```text
Give users and systems only the access they need, and no more.
```

This is one of the most important authorization ideas.

A user who only needs to read reports should not have delete permissions.

A service that only sends emails should not have full database admin access.

A support agent should not automatically have access to every private field.

Least privilege limits damage.

If an account or service is compromised, the attacker gets only the permissions that identity had.

### Least Privilege for Services

Least privilege is not only for human users.

Backend services need it too.

Example:

```text
Email service only needs permission to send emails.
Image service only needs access to image storage.
Analytics service only needs read access to event data.
```

If every service has admin access to everything, one compromised service can damage the whole system.

Good authorization limits what each service can do.

That is why API keys, service accounts, and database users should also have scoped permissions.

---

## My Biggest Realization

Authorization is not just roles.

Roles are one way to organize access, but the deeper idea is:

```text
Subject + resource + action + policy = authorization decision
```

That model helps me think beyond simple admin checks.

It also reminds me that authorization belongs on the server.

The frontend can hide buttons, but the backend must enforce rules.

## Part 5 Complete!

## Final Summary

**1. Authorization answers "What can you do?"**

It happens after authentication and decides whether an identity can perform an action.

**2. Authorization decisions involve subjects, resources, actions, and policies**

This makes access control more concrete and testable.

**3. RBAC is simple and common**

Users receive roles, and roles contain permissions.

**4. ABAC is flexible and context-aware**

It uses attributes from users, resources, actions, and environments.

**5. Least privilege is the guiding principle**

Give each user or system only the access they need.

### Checkpoint Questions

**What is RBAC?**

A model where permissions are grouped into roles and roles are assigned to users.

**What is ABAC?**

A model where access decisions are based on attributes and policies.

**What is a claim?**

A statement about a user or client, often stored in a token.

**What is least privilege?**

The practice of granting only the minimum access needed.
