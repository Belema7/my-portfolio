# Backend from First Principles — Day 5 (Part 6)

# Auth in Practice: Middleware, Roles, and Permissions

> *"The theory becomes practical when I can see the request move through middleware: first authenticate the caller, then authorize the action, then run the controller."*

---

## Introduction

So far, I have learned the concepts:

```text
Authentication = Who are you?
Authorization = What can you do?
```

Now I want to see the flow in code.

The examples in this part use Express-style JavaScript because middleware makes the sequence easy to see.

The same ideas apply in other frameworks:

```text
Verify identity
Attach user to request
Check permissions
Run protected handler
```

The exact syntax changes across frameworks, but the shape of the security flow stays the same.

### Before the Code: What Is Middleware?

For a beginner, middleware can sound mysterious.

In Express, middleware is just a function that runs before the final route handler.

It receives:

```text
req  = the incoming request
res  = the outgoing response object
next = a function that moves to the next middleware
```

A middleware can:

```text
Read headers
Validate data
Attach information to req
Stop the request with an error response
Call next() to continue
```

For authentication and authorization, middleware is useful because protected routes need the same checks again and again.

Instead of rewriting token validation in every route, I can put it in one middleware.

---

## Topic 6.1 — Authentication Middleware

Authentication middleware checks whether the request has a valid identity.

For a JWT-based API, that usually means reading the `Authorization` header.

```http
Authorization: Bearer eyJhbGciOi...
```

Example middleware:

```js
const authenticate = (req, res, next) => {
  const authHeader = req.headers.authorization;

  if (!authHeader) {
    return res.status(401).json({
      error: "Unauthorized",
      message: "No token provided",
    });
  }

  const [scheme, token] = authHeader.split(" ");

  if (scheme !== "Bearer" || !token) {
    return res.status(401).json({
      error: "Unauthorized",
      message: "Invalid authorization header",
    });
  }

  try {
    const decoded = jwt.verify(token, JWT_SECRET);
    req.user = decoded;
    return next();
  } catch (error) {
    return res.status(401).json({
      error: "Unauthorized",
      message: "Invalid or expired token",
    });
  }
};
```

The middleware does three important things:

| Step | Purpose |
| --- | --- |
| Read token | Find the credential |
| Verify token | Prove it is valid and not expired |
| Attach user | Make identity available to later middleware |

After this middleware succeeds, later code can use `req.user`.

That is the bridge from authentication to authorization.

### Code Walkthrough Line by Line

This line reads the auth header:

```js
const authHeader = req.headers.authorization;
```

The client usually sends something like:

```http
Authorization: Bearer eyJhbGciOi...
```

The word `Bearer` means:

```text
The client is carrying a token and presenting it as proof.
```

This line splits the header:

```js
const [scheme, token] = authHeader.split(" ");
```

So this:

```text
Bearer abc123
```

becomes:

```text
scheme = Bearer
token = abc123
```

Then `jwt.verify()` checks whether the token is trustworthy:

```js
const decoded = jwt.verify(token, JWT_SECRET);
```

If verification succeeds, the decoded claims are attached to the request:

```js
req.user = decoded;
```

That means the next middleware can ask:

```text
What role does this user have?
What permissions does this user have?
What userId is this?
```

This is the exact moment authentication prepares the request for authorization.

## Topic 6.2 — Role-Based Authorization Middleware

Once the request has a user, the backend can check roles.

```js
const authorizeRoles = (requiredRoles) => {
  return (req, res, next) => {
    if (!req.user) {
      return res.status(401).json({
        error: "Unauthorized",
      });
    }

    const roles = req.user.roles || [];
    const hasRole = roles.some((role) => requiredRoles.includes(role));

    if (!hasRole) {
      return res.status(403).json({
        error: "Forbidden",
        message: "You do not have the required role",
      });
    }

    return next();
  };
};
```

Usage:

```js
app.get(
  "/api/admin/users",
  authenticate,
  authorizeRoles(["ADMIN"]),
  (req, res) => {
    res.json({ users: [] });
  }
);
```

The order matters:

```text
authenticate → authorizeRoles → handler
```

If authorization runs before authentication, there may be no user identity to check.

### Why This Middleware Returns 401 or 403

Inside authorization middleware, there are two different failure cases.

If `req.user` does not exist, authentication did not happen correctly.

That is a `401`.

```js
if (!req.user) {
  return res.status(401).json({ error: "Unauthorized" });
}
```

If `req.user` exists but the user lacks the role, authentication succeeded but authorization failed.

That is a `403`.

```js
if (!hasRole) {
  return res.status(403).json({ error: "Forbidden" });
}
```

This is a practical version of the Day 5 rule:

```text
401 = I do not know who you are.
403 = I know who you are, but you cannot do this.
```

## Topic 6.3 — Permission-Based Authorization Middleware

Roles are useful, but permissions are often more precise.

Instead of asking:

```text
Is this user an admin?
```

The backend can ask:

```text
Does this user have user:delete?
```

Example middleware:

```js
const requirePermissions = (requiredPermissions) => {
  return (req, res, next) => {
    if (!req.user) {
      return res.status(401).json({
        error: "Unauthorized",
      });
    }

    const permissions = req.user.permissions || [];
    const hasAllPermissions = requiredPermissions.every((permission) =>
      permissions.includes(permission)
    );

    if (!hasAllPermissions) {
      return res.status(403).json({
        error: "Forbidden",
        message: "Missing required permission",
      });
    }

    return next();
  };
};
```

Usage:

```js
app.delete(
  "/api/users/:id",
  authenticate,
  requirePermissions(["user:delete"]),
  (req, res) => {
    res.json({ message: "User deleted" });
  }
);
```

Permission checks are often better than role checks when the system grows.

Roles can still exist, but permissions describe the actual ability.

### Roles vs Permissions in Code

A role is a label:

```text
ADMIN
MANAGER
USER
```

A permission is an ability:

```text
user:read
user:delete
project:update
invoice:refund
```

Roles can contain permissions:

```json
{
  "role": "ADMIN",
  "permissions": ["user:read", "user:delete", "project:update"]
}
```

When checking access, permissions often make the route easier to understand:

```js
requirePermissions(["invoice:refund"])
```

That says exactly what the route needs.

The route does not need to know every role that might include that permission.

## Topic 6.4 — Login Flow

Authentication usually begins at login.

The backend receives credentials, validates them, and creates a token or session.

```js
app.post("/login", async (req, res) => {
  const { username, password } = req.body;

  const user = await User.findOne({ username });

  if (!user) {
    return res.status(401).json({
      error: "Invalid credentials",
    });
  }

  const passwordMatches = await bcrypt.compare(password, user.passwordHash);

  if (!passwordMatches) {
    return res.status(401).json({
      error: "Invalid credentials",
    });
  }

  const token = jwt.sign(
    {
      userId: user.id,
      username: user.username,
      roles: user.roles,
      permissions: user.permissions,
    },
    JWT_SECRET,
    { expiresIn: "15m" }
  );

  return res.json({ token });
});
```

Two security details matter here:

| Detail | Why it matters |
| --- | --- |
| `bcrypt.compare()` | The backend compares against a password hash, not a plain password |
| Short expiry | Limits damage if an access token is stolen |

In a browser app, the token may be sent in an `HttpOnly`, `Secure`, `SameSite` cookie instead of a JSON response body.

The storage choice depends on the client type and security model.

### Why the Error Message Is Generic

The example returns:

```json
{
  "error": "Invalid credentials"
}
```

for both a missing user and a wrong password.

That is intentional.

If the server says:

```text
This username does not exist.
```

an attacker can use the login endpoint to discover real usernames.

A generic message gives less information away.

The backend can still log the detailed reason internally, but the public response should be careful.

### Where Refresh Tokens Fit

The example creates a short-lived access token:

```js
{ expiresIn: "15m" }
```

In a real app, a user should not have to log in every 15 minutes.

That is why many systems use refresh tokens.

The simplified idea:

```text
Access token: short-lived, used for API requests.
Refresh token: longer-lived, used to get new access tokens.
```

Refresh tokens need careful storage, rotation, and revocation.

They are powerful credentials.

## Topic 6.5 — Complete Protected Route Flow

Now the full flow can be combined:

```js
app.delete(
  "/api/users/:id",
  authenticate,
  authorizeRoles(["ADMIN"]),
  requirePermissions(["user:delete"]),
  async (req, res) => {
    const targetUserId = Number(req.params.id);

    if (req.user.userId === targetUserId) {
      return res.status(403).json({
        error: "Forbidden",
        message: "You cannot delete yourself",
      });
    }

    await deleteUser(targetUserId);

    return res.json({
      message: "User deleted successfully",
    });
  }
);
```

The request passes through layers:

```text
1. Is there a valid token?
2. Does the user have the ADMIN role?
3. Does the user have user:delete permission?
4. Does the business rule allow this specific delete?
5. Run the controller.
```

That last business rule is important.

Even if a user has `user:delete`, the system may still forbid deleting yourself.

Authorization can be both general and resource-specific.

### Why Multiple Checks Are Normal

At first, the route can look like it has too many checks.

But each check answers a different question:

| Check | Question |
| --- | --- |
| `authenticate` | Who is making the request? |
| `authorizeRoles(["ADMIN"])` | Is this user in an admin role? |
| `requirePermissions(["user:delete"])` | Does this user have delete ability? |
| `req.user.userId === targetUserId` | Is this specific delete blocked by business rules? |

Security often works in layers.

One check may be broad.

Another check may be precise.

Together, they make the route safer and easier to reason about.

## Topic 6.6 — Nested Resource Checks

Nested routes often require ownership or relationship checks.

Example:

```http
GET /users/15/orders/99
```

The backend should not only check:

```text
Can this user read orders?
```

It may also need to check:

```text
Does order 99 belong to user 15?
Is the authenticated user allowed to view user 15's orders?
```

Example:

```js
app.get(
  "/api/users/:userId/orders/:orderId",
  authenticate,
  async (req, res) => {
    const userId = Number(req.params.userId);
    const orderId = Number(req.params.orderId);

    const canViewOwnOrders = req.user.userId === userId;
    const canViewAllOrders = req.user.permissions?.includes("order:read:any");

    if (!canViewOwnOrders && !canViewAllOrders) {
      return res.status(403).json({
        error: "Forbidden",
      });
    }

    const order = await findOrderForUser(orderId, userId);

    if (!order) {
      return res.status(404).json({
        error: "Order not found",
      });
    }

    return res.json(order);
  }
);
```

Nested routes remind me that authorization is often about relationships, not just roles.

### Why "Find by Both IDs" Helps

This line in the example is important:

```js
const order = await findOrderForUser(orderId, userId);
```

The backend should not only find:

```text
Order 99
```

It should find:

```text
Order 99 that belongs to User 15
```

That prevents a common authorization bug where a user changes a URL parameter to access someone else's resource.

Example:

```text
/users/15/orders/99
/users/16/orders/99
```

If the backend does not verify the relationship, a user may access data they should not see.

## My Biggest Realization

Middleware makes the security pipeline visible.

The request should move through identity first, permission second, business rules third.

```text
Authenticate.
Authorize.
Then execute.
```

That order keeps protected route logic easier to reason about.

## Part 6 Complete!

## Final Summary

**1. Authentication middleware verifies identity**

It validates the token and attaches the decoded user to the request.

**2. Authorization middleware checks access**

It uses roles, permissions, or resource rules to decide whether the request can continue.

**3. Middleware order matters**

Authentication should run before authorization.

**4. Login should validate hashed passwords**

Use `bcrypt`, `Argon2`, or `scrypt`, never plain text password storage.

**5. Business rules still matter**

Even users with broad permissions may be blocked by resource-specific rules.

### Checkpoint Questions

**What should authentication middleware do?**

Verify the credential, reject invalid requests, and attach identity to the request.

**What status code should missing or invalid tokens return?**

`401 Unauthorized`.

**What status code should missing permissions return?**

`403 Forbidden`.

**Why should authorization be checked on the server?**

Because clients can bypass the frontend and call the API directly.
