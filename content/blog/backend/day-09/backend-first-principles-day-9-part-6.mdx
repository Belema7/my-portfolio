# Idempotency: Making Retries Safe

> *“Networks can lose responses even after servers complete work, so a reliable API must expect clients to retry.”*

## The Ambiguous Failure

Part 5 described outcomes with status codes. But sometimes the client receives no outcome at all.

```text
Client sends Create Order
  ↓
Server creates and charges successfully
  ↓
Network drops response
  ↓
Client sees timeout and does not know what happened
```

Retrying might create a second order and second charge. Not retrying might leave the user thinking nothing happened.

This is why idempotency is a distributed-systems concern, not just a double-click UI trick.

## Mathematical Idea, HTTP Meaning

An operation is idempotent when applying it repeatedly has the same intended effect as applying it once.

```text
f(f(x)) = f(x)
```

HTTP method semantics classify:

| Method | Safe | Idempotent by semantics |
| --- | --- | --- |
| GET | Yes | Yes |
| HEAD | Yes | Yes |
| OPTIONS | Yes | Yes |
| PUT | No | Yes |
| DELETE | No | Yes |
| POST | No | No |
| PATCH | No | Depends on patch operation |

The intended effect matters, not identical response codes, timestamps, logs, or network bytes.

## Naturally Idempotent Examples

```http
PUT /users/user_123/preferences

{ "theme": "dark" }
```

Repeating replacement leaves the same theme.

```http
DELETE /books/book_123
```

After repeated requests, the book remains absent. A later response can still be `404`.

## Non-Idempotent Examples

```http
POST /orders
```

Repeating may create multiple orders.

```json
{ "operation": "increment", "points": 10 }
```

Repeating increments repeatedly.

## Idempotency Keys

For an operation that must be safely retryable, the client generates a unique key for one logical attempt:

```http
POST /orders
Idempotency-Key: 8a0d5b8e-...
```

The server scopes the key, normally by authenticated account and endpoint/operation.

```text
new key + request
  → reserve key
  → process operation
  → persist outcome
  → return response

same key + same request
  → replay stored outcome

same key + different request
  → reject conflict
```

## Why an In-Memory Map Is Not Production-Grade

An example `Map` loses data on restart, is not shared between application instances, and does not handle concurrent requests atomically.

A durable store needs a unique constraint:

```sql
CREATE TABLE idempotency_records (
  account_id text NOT NULL,
  operation text NOT NULL,
  key text NOT NULL,
  request_hash text NOT NULL,
  status text NOT NULL,
  response_status integer,
  response_body jsonb,
  resource_id text,
  created_at timestamptz NOT NULL,
  expires_at timestamptz NOT NULL,
  PRIMARY KEY (account_id, operation, key)
);
```

The primary key prevents two concurrent first requests from both owning the same logical operation.

## Request Fingerprinting

If a client reuses the key with a different body, replaying the old result is dangerous.

Compute a canonical request fingerprint from relevant method, target, media type, and normalized body:

```text
same key + same fingerprint → retry
same key + different fingerprint → 409 conflict
```

Canonicalization must be deterministic. Secrets should not be exposed in logs, and hashes do not automatically make sensitive raw data safe to retain.

## Concurrent First Requests

Two identical requests may arrive simultaneously:

```text
Request A inserts key → succeeds, status processing
Request B inserts key → unique conflict
Request B reads record → waits/polls or returns in-progress response
Request A stores outcome
```

The behavior for “in progress” must be documented. The server might wait briefly, return `409`, `202`, or another deliberate response with retry guidance.

## Store the Outcome Atomically

The idempotency record and business write must not drift.

```text
create order succeeds
process crashes before idempotency outcome saved
retry creates second order
```

Where possible, create the resource and finalize the idempotency record in one database transaction. For external payment providers, combine provider idempotency, durable local state, and reconciliation.

## What Response Is Replayed?

APIs commonly replay the original status and body, including known failures after processing began. Whether transient `500` responses are stored depends on policy.

Headers such as the original request ID may not be appropriate to replay unchanged. Documentation should define replay behavior.

```http
Idempotency-Replayed: true
```

can make retries observable, though this is an API-specific header.

## Key Lifetime and Garbage Collection

Records cannot remain forever without cost. Expiration must exceed the maximum realistic retry window.

Reusing an expired key can create a new operation, so clients should generate high-entropy unique keys per logical attempt and not recycle them.

## Idempotency Versus Deduplication

Deduplication may say two messages look alike. Idempotency gives one logical operation a stable identity and defined repeated behavior.

Two legitimate identical coffee orders should both succeed if they use different keys. Body equality alone must not merge them.

## Client Responsibilities

The client should:

- generate a unique unpredictable key;
- reuse it only for retries of the same logical operation;
- keep the same request content;
- handle in-progress and replay responses;
- use bounded retry with backoff;
- not generate a new key merely because a response timed out.

## Server Pseudocode

```ts
async function createOrder(req: Request, res: Response) {
  const key = parseIdempotencyKey(req);
  const fingerprint = fingerprintRequest(req);

  const claim = await idempotencyStore.claim({
    accountId: req.context.user.accountId,
    operation: "create-order",
    key,
    fingerprint,
  });

  if (claim.kind === "mismatch") {
    return res.status(409).json({ error: { code: "KEY_REUSED" } });
  }

  if (claim.kind === "completed") {
    return res.status(claim.status).json(claim.body);
  }

  if (claim.kind === "processing") {
    return res.status(202).json({ status: "processing" });
  }

  const outcome = await orderService.create(command, claim.transaction);
  await claim.complete({ status: 201, body: outcome.response });

  return res.status(201).json(outcome.response);
}
```

Real code must handle transaction boundaries, crashes, and external effects carefully.

## Testing Idempotency

```text
new key creates once
same key/same body replays
same key/different body conflicts
two concurrent requests create once
restart preserves records
expired key follows documented policy
processing request follows documented policy
provider timeout reconciles without double charge
```

Concurrency tests require a real shared store, not only mocks.

## Idempotency State Machine

```text
reserved/processing
  ├─→ completed (replayable outcome)
  └─→ recoverable/failed according to policy
```

A record stuck in processing after a crash needs recovery. A lease timestamp can let a worker determine whether processing is genuinely active or abandoned, but takeover must avoid two processors running concurrently.

## Transaction Pattern

```ts
await db.transaction(async (tx) => {
  const claim = await tx.idempotency.claim(scope, key, fingerprint);
  if (!claim.isOwner) return claim.existingOutcome;

  const order = await tx.orders.create(command);
  const response = toOrderResponse(order);

  await tx.idempotency.complete(claim.id, {
    status: 201,
    body: response,
    resourceId: order.id,
  });

  return response;
});
```

This works when business state and idempotency records share a database. Cross-service workflows require durable orchestration and provider-level idempotency.

## Scope Prevents Cross-User Replay

Using only the key as a global identifier could let one account collide with another. Scope includes the authenticated principal/tenant and operation.

```text
(tenant, actor/account, operation, key)
```

Authorization still runs on retries. A stored response must not be replayed to a caller who no longer has permission unless policy explicitly allows it.

## Idempotency and Webhooks

Webhook providers may deliver the same event more than once. The receiver stores the provider event ID or logical operation ID with a unique constraint before applying effects.

```text
receive event
verify signature over raw body
claim event ID
apply transaction
mark processed
acknowledge
```

Acknowledging before durable processing risks data loss; processing before deduplication risks repeated effects.

## What Not to Store

Persisting full request and response bodies can retain credentials or personal data. Store only what replay and audit policy require, encrypt/protect it appropriately, and expire it according to retention rules.

## Operational Metrics

Track new claims, replays, fingerprint conflicts, in-progress collisions, abandoned claims, processing duration, and cleanup. A sudden replay spike may indicate network trouble or a client retry bug.

## Checkpoint Questions

### Why is idempotency needed even without double-clicks?

Clients retry after timeouts because they cannot know whether the server completed the operation before the response was lost.

### Is DELETE idempotent if the second call returns 404?

Yes. The intended state effect remains that the resource is absent.

### Why store a request fingerprint?

It prevents one key from being reused for a different operation payload.

### Why is an in-memory map insufficient?

It is lost on restart, not shared across instances, and cannot provide durable atomic concurrency guarantees.
