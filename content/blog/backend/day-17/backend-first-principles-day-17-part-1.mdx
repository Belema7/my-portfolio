# Configuration Is the DNA of Your Application

> *“Same code, different settings, completely different behaviour.”*

## A Definition First

**Configuration management** is the systematic approach to organizing, storing, accessing, and maintaining **all the settings** of a backend application.

The key words are *all the settings*.

I like to think of configuration as the **DNA of the application**. The code describes what the application *can* do. The configuration decides **how that code actually runs** in each environment.

```text
Code          → what the application can do
Configuration → how it behaves right now, in this environment
```

## The Common Misunderstanding

When most people hear “configuration management,” they think of secrets:

```text
🔑 Database password / connection URL
🔑 JWT secret
🔑 API keys for external services (email, payments)
```

Those are important. But thinking of configuration as *only* secrets is like saying a car is just its engine. The engine matters most, but you are ignoring 90% of the car.

Configuration also decides:

- **How the application starts up**
- **How it connects** to external services
- **How it behaves** in different environments
- **What it logs**, whether it logs, and where the logs go
- **Where metrics are sent** — performance metrics and business metrics
- **Which features are enabled** in this deployment, and **for which users**

Configuration affects many important behaviours of a backend, not just its passwords.

## A Real Example: An E-Commerce Backend

Imagine I am building the backend for an e-commerce platform. Its configuration might include:

| Setting | Example |
| --- | --- |
| **Database connection details** | Host, port, username, password, timeouts |
| **Payment processor API keys** | Stripe API key |
| **Feature flags** | Use the new checkout flow or the old one |
| **Performance tuning** | Database connection pool size |
| **Security settings** | Session timeout |
| **Business rules** | Maximum order amount per user |

The feature flag is a good example of configuration that is *not* a secret. Say I built a new checkout flow. A flag decides whether the old or new flow runs — and it can even enable the new flow for **some users** and keep the old one for others.

## Not All Configuration Is the Same

Each of those settings has different **characteristics**, and those characteristics decide how it should be stored and protected.

### Sensitive vs Non-Sensitive

```text
Sensitive     → Stripe API key, database password, JWT secret
                (if leaked, they can cause serious damage and loss)

Non-sensitive → log level, port, feature flags, max order amount
                (not secret, but they control how the app behaves)
```

### How Often It Changes

```text
Frequently    → feature flags, rollout percentages
Rarely        → database host, business limits (once a month or quarter)
```

### Same or Different Across Environments

```text
Same everywhere      → app name, API version, some business rules
Different per env    → database URL, log level, pool size, API keys
```

Combining these gives each setting a profile:

| Setting | Sensitive? | Changes often? | Differs per environment? |
| --- | --- | --- | --- |
| Database password | Yes | Rarely (on rotation) | Yes |
| Log level | No | Sometimes | Yes |
| New checkout flag | No | Often | Often |
| Max order amount | No | Rarely | Usually no |
| Stripe API key | Yes | Rarely | Yes (test vs live keys) |

Understanding these profiles is the foundation for everything else this day covers: types, storage, environments, and security.

## The Big Promise of Configuration

Good configuration management means:

> I can change how the application behaves **without changing its code**.

Switch the log level, turn on a feature, raise the pool size, point to a different database — all by changing configuration, not by editing, reviewing, and redeploying code.

## Checkpoint Questions

### What is configuration management?

The systematic approach to organizing, storing, accessing, and maintaining all the settings of an application.

### Why is “configuration = secrets” an incomplete view?

Because configuration also controls startup, connections, environment behaviour, logging, metrics, and features. Secrets are only one part.

### What characteristics make configuration values different from each other?

Whether they are sensitive, how often they change, and whether they differ between environments.
