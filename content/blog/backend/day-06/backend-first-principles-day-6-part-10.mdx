# Backend from First Principles — Day 6 (Part 10)

# Validation Pitfalls and Production Best Practices

> *“Good validation is strict about the contract, careful about security, and predictable for every client that depends on it.”*

---

## Introduction

By this point, validation sounds straightforward:

```text
Write rules.
Check the request.
Reject invalid input.
```

But production bugs often hide in the details.

A developer validates the JSON body but forgets the path parameter. Another developer converts `"false"` using `Boolean()` and gets `true`. A service checks uniqueness but forgets that two requests can run at the same time.

The code contains validation, yet the system is still unsafe.

This part is about those traps—the mistakes that look reasonable when I am starting and the habits that make an API dependable.

## A Beginner Mistake: One Giant Validation Function

When all rules are described as “validation,” it is tempting to create one enormous function:

```js
async function validateEverything(req) {
  // body shape
  // user permissions
  // database lookups
  // inventory rules
  // response formatting
}
```

Soon the function knows about HTTP, users, orders, the database, and error status codes. It becomes difficult to test and harder to reuse.

The solution is not to stop validating. It is to give each rule an owner:

```text
Boundary schema → request structure and types
Authentication → caller identity
Service/domain → business meaning
Database → final storage constraints
Error mapper → public HTTP response
```

Validation code can exist and still fail to protect a system. The most dangerous mistakes are often not missing `if` statements. They are unclear ownership, permissive coercion, inconsistent schemas, and false assumptions about what validation can prevent.

## Pitfall 1: Validating Only the Body

An endpoint may validate JSON while trusting path parameters, query strings, headers, cookies, or files.

The fix is to model the whole request surface:

```js
const requestSchema = z.object({
  params: paramsSchema,
  query: querySchema,
  body: bodySchema,
  headers: selectedHeadersSchema,
});
```

Validate selected headers instead of passing the entire header object into application logic.

## Pitfall 2: Trusting Frontend or TypeScript Checks

Browser validation can be bypassed. TypeScript types are erased at runtime. API input must be validated where it enters the trusted server process.

Treat request data as `unknown` until a runtime parser proves its shape.

## Pitfall 3: Passing Request Bodies Directly to the Database

This is concise and dangerous:

```js
await db.user.update({
  where: { id },
  data: req.body,
});
```

It can enable mass assignment and makes future database fields part of the public API accidentally.

Create explicit allowlisted data:

```js
const changes = {
  displayName: input.displayName,
  biography: input.biography,
};
```

## Pitfall 4: Broad Coercion

Convenient coercion can turn mistakes into valid-looking values:

```js
Boolean("false") // true
parseInt("12px") // 12
Number("")       // 0
```

Use exact parsers, document accepted forms, and reject ambiguous input.

### Why “Helpful” Conversion Can Be Unhelpful

Suppose an API silently changes every invalid page number to page 1.

The frontend accidentally sends:

```http
GET /products?page=undefined
```

The API returns page 1, so no one notices the frontend bug. Users keep seeing the wrong page while both applications appear successful.

A clear `400 Bad Request` exposes the broken contract early. Strictness can make development easier because failures appear near their cause.

## Pitfall 5: Confusing Validation With Injection Defense

An email validator does not prevent SQL injection. A text length limit does not prevent XSS.

Use defenses designed for the destination:

| Destination | Primary defense |
| --- | --- |
| SQL | Parameterized queries / safe ORM APIs |
| HTML | Context-aware output encoding |
| Shell | Avoid shell construction; use argument APIs |
| Redirect URL | Allowlisted origins and schemes |
| File path | Server-generated paths and strict containment |

Validation is an additional allowlist, not a substitute for sink-specific protection.

## Pitfall 6: Friendly Pre-Checks Without Constraints

Checking whether an email exists before insertion does not guarantee uniqueness under concurrency. Protect important invariants with database constraints, transactions, and atomic operations, then map constraint failures into clear domain errors.

## Pitfall 7: Unlimited Input

A syntactically valid payload can still be abusive. Set limits for:

- request body bytes;
- header size and count;
- string length;
- array length and nesting depth;
- file bytes and dimensions;
- pagination page size;
- decompressed content;
- regex complexity and processing time.

Reject oversized input before expensive parsing whenever possible.

## Pitfall 8: Inconsistent Error Shapes

One endpoint returns a string, another an array, and a third exposes a stack trace. Clients become complicated and internal details leak.

Adopt a stable error envelope:

```json
{
  "type": "validation_error",
  "message": "The request contains invalid fields.",
  "errors": [
    { "field": "email", "code": "invalid_format" }
  ],
  "requestId": "req_123"
}
```

Do not include passwords, tokens, stack traces, raw SQL, or secret configuration in logs or responses.

## Best Practice: Use Declarative Schemas

Libraries reduce repetitive code and standardize nested error paths. Common options include:

| Ecosystem | Examples |
| --- | --- |
| JavaScript/TypeScript | Zod, Joi, Valibot, express-validator |
| Python | Pydantic, Marshmallow |
| Java | Jakarta Bean Validation / Hibernate Validator |
| .NET | Data Annotations, FluentValidation |

The library is not the architecture. Choose one based on runtime support, type inference, async rule strategy, error customization, performance, and team familiarity.

Keep business rules in named service or domain operations instead of hiding every database call inside a field schema.

### Libraries Help, but They Do Not Think for Us

A schema library can check that `quantity` is an integer from 1 to 100.

It cannot decide by itself:

```text
Whether this product may be sold
Whether this user has permission
Whether inventory is current
Whether an order needs a transaction
Whether an error reveals sensitive information
```

Libraries reduce repetitive mechanics. Developers still define the contract and architecture.

## Best Practice: Validate Early, Preserve Invariants Deeply

Use layers intentionally:

```text
HTTP boundary → shape, type, parsing, limits
Service/domain → business meaning, authorization, state transitions
Database → uniqueness, references, atomic constraints
Output boundary → explicit serialization and encoding
```

This is defense in depth with clear ownership.

## Best Practice: Test the Contract

Useful tests include:

- one below, at, and one above each boundary;
- omitted, null, empty, and whitespace-only values;
- wrong primitive and container types;
- unknown properties;
- invalid nested elements;
- Unicode and unusually long values;
- duplicate and conflicting requests;
- concurrency-sensitive invariants;
- authorization differences by actor;
- stable error codes and field paths.

Fuzz tests can generate unexpected JSON shapes, while contract tests keep clients and servers aligned.

### The Boundary Test Pattern

If a username allows 3–30 characters, do not test only a normal value such as 10.

Test around the edges:

```text
2 characters  → should fail
3 characters  → should pass
30 characters → should pass
31 characters → should fail
```

This is boundary-value testing. Many bugs hide one step outside the accepted range.

Also test the forms that humans frequently confuse:

```text
field missing
field is null
field is empty string
field contains only spaces
field has wrong type
field has correct type but wrong meaning
```

## Best Practice: Observe Rejections Safely

Metrics can reveal broken clients and attacks:

```text
validation failures by endpoint and code
payload-too-large rejections
rate-limit events
conflict frequency
unexpected-field frequency
```

Log request IDs and safe metadata, not full sensitive payloads. Sudden spikes can indicate a deployment mismatch or probing activity.

## Best Practice: Evolve Contracts Deliberately

Tightening validation can break existing clients. Before changing a rule:

```text
measure current rejected/accepted forms
document the new contract
update clients
consider a transition period or version
deploy observability
then enforce the stricter rule
```

Validation is part of API compatibility.

## A Practical Review Checklist

Before shipping an endpoint, ask:

- Are all client-controlled sources covered?
- Are unknown fields handled explicitly?
- Are coercions exact and documented?
- Are sizes and ranges bounded?
- Are business invariants protected under concurrency?
- Are authorization and validation separate?
- Are database and output boundaries safe?
- Are errors stable, useful, and non-sensitive?
- Are boundary and failure cases tested?

## A Small Before-and-After Example

### Before

```js
app.post("/products", async (req, res) => {
  const product = await db.product.create({ data: req.body });
  res.json(product);
});
```

This route trusts every field, has no size or type policy, mixes HTTP and persistence, and may return internal database fields.

### After

```js
app.post("/products", authenticateAdmin, async (req, res, next) => {
  try {
    const parsed = createProductSchema.safeParse(req.body);

    if (!parsed.success) {
      return res.status(400).json(formatValidationErrors(parsed.error));
    }

    const product = await productService.create(parsed.data);

    return res.status(201).json({
      id: product.id,
      name: product.name,
      price: product.price,
    });
  } catch (error) {
    next(error);
  }
});
```

The second example makes the checkpoints visible. Authentication, boundary validation, business logic, persistence, and response shaping have distinct responsibilities.

## Checkpoint Questions

### Why is spreading `req.body` into a database operation dangerous?

It lets the client influence every matching database field, including fields the public endpoint never intended to expose.

### Does input validation prevent SQL injection by itself?

No. Use parameterized queries or safe ORM APIs for SQL. Validation is an additional contract, not a replacement for destination-specific defenses.

### Why should payload and collection sizes be limited?

A value can be structurally valid while causing excessive memory, CPU, storage, or database work.

### What should be tested around every numeric or length boundary?

One value below the minimum, the minimum itself, the maximum itself, and one value above the maximum.

## What I Learned

Professional validation is not maximum strictness everywhere. It is a deliberate contract with clear ownership, safe conversion, bounded cost, authoritative constraints, and useful failures.
