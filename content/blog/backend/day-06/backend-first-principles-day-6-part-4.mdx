# Backend from First Principles — Day 6 (Part 4)

# Syntactic Validation: Does the Input Look Right?

> *“Syntactic validation checks the shape of a message before the application tries to understand its meaning.”*

---

## Introduction

Imagine someone sends me a letter.

I expect the letter to contain:

```text
Name
Email address
Phone number
```

Instead, I open it and find the name missing, the email cut in half, and twenty pages of unrelated text.

Before I can decide whether the information is true, I have a more basic problem: the message does not follow the expected structure.

That is the problem syntactic validation solves.

The word **syntactic** comes from syntax—the rules that describe how something is arranged. In normal language, syntax helps words form understandable sentences. In an API, syntax helps fields form an understandable request.

Syntactic validation checks whether input follows the structure and format promised by an API contract.

It answers questions such as:

- Is the body an object rather than an array?
- Are the required fields present?
- Does the string stay within its length limit?
- Does the identifier follow the expected pattern?
- Are nested objects shaped correctly?

It is the grammar check of an API request.

## Syntax in Everyday Life

Think about a paper form at a hospital.

The form has labeled boxes:

```text
Full name: __________________
Date of birth: ______________
Phone number: _______________
Emergency contact: __________
```

The hospital expects information in particular places and formats. If someone writes their whole life story across every box, the information may contain useful facts, but the form is not usable.

An API schema is like that form.

It says:

```text
These fields are accepted.
These fields are required.
These values have maximum sizes.
These strings follow documented patterns.
This nested information belongs in this shape.
```

Syntactic validation checks whether the client filled in the digital form correctly.

## Shape Comes First

Assume an endpoint expects:

```json
{
  "name": "Alice",
  "email": "alice@example.com",
  "address": {
    "country": "SO",
    "city": "Mogadishu"
  },
  "tags": ["backend", "api"]
}
```

Syntactic rules can define:

```text
body: object
name: required string, 1–80 characters
email: required string, email-like format
address: optional object
address.country: exactly two letters
tags: optional array, at most 10 items
each tag: non-empty string, at most 30 characters
```

These rules prevent deeper code from repeatedly asking whether `address` exists or whether `tags.map` is safe to call.

## Required Does Not Always Mean Non-Empty

These values are different:

```json
{}
{ "name": null }
{ "name": "" }
{ "name": "   " }
```

The field is missing in the first request, explicitly null in the second, empty in the third, and whitespace-only in the fourth. A good schema defines each case rather than collapsing them accidentally.

For a display name, the policy could be:

```text
required → must exist
non-null → null is not allowed
trimmed → surrounding whitespace is removed
min length 1 → empty after trimming is rejected
max length 80 → storage and UI limits are respected
```

## Format Checks

Common format checks include:

| Value | Possible syntactic rule |
| --- | --- |
| Email | A practical email parser or library |
| Phone | An agreed international or local representation |
| URL | Parsed URL with allowed schemes |
| UUID | Exact UUID variant/pattern required by the API |
| Country code | Supported ISO-style code format |
| Date string | Exact documented representation |

Regex can help with narrow patterns:

```js
const phonePattern = /^\d{3}-\d{3}-\d{4}$/;

if (!phonePattern.test(input.phone)) {
  throw new ValidationError("Use XXX-XXX-XXXX format");
}
```

But complex standards are rarely served well by a giant hand-written regex. For emails, URLs, international phone numbers, and dates, a tested parser or validation library is usually clearer.

Syntactic validity is also not proof of ownership. A well-formed email must still be verified if the system needs to know that the user controls it.

## Length and Size Limits Are Security Controls

Length validation is not cosmetic. Without limits, a client can submit a 20-megabyte biography where the product expects 500 characters.

Limits should exist at several levels:

```text
HTTP server/body parser → maximum request size
schema → maximum string, array, and object size
database → appropriate column and record constraints
file pipeline → maximum bytes, dimensions, and processing cost
```

When Unicode matters, “length” may mean bytes, code points, or user-perceived characters. The contract should choose the measure that matches storage and product behavior.

## Unknown Fields Need a Policy

Suppose registration expects `name` and `email`, but the client sends:

```json
{
  "name": "Alice",
  "email": "alice@example.com",
  "role": "admin"
}
```

Blindly passing the body to an ORM can create a mass-assignment vulnerability.

Safe strategies are:

- reject unknown fields;
- strip unknown fields and construct an allowlisted object;
- explicitly map every accepted field.

For public write APIs, strict objects are often the clearest default. Silent stripping can be useful for compatibility, but it can also hide client bugs. The choice should be documented.

## A Focused JavaScript Example

```js
function validateProfileSyntax(value) {
  const errors = [];

  if (!value || typeof value !== "object" || Array.isArray(value)) {
    return [{ field: "body", code: "expected_object" }];
  }

  const allowed = new Set(["name", "email", "phone"]);
  for (const key of Object.keys(value)) {
    if (!allowed.has(key)) {
      errors.push({ field: key, code: "unknown_field" });
    }
  }

  const name = typeof value.name === "string" ? value.name.trim() : value.name;

  if (name === undefined) {
    errors.push({ field: "name", code: "required" });
  } else if (typeof name !== "string" || name.length < 1 || name.length > 80) {
    errors.push({ field: "name", code: "invalid_length" });
  }

  const emailPattern = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
  if (typeof value.email !== "string" || !emailPattern.test(value.email)) {
    errors.push({ field: "email", code: "invalid_format" });
  }

  return errors;
}
```

In production, a schema library can express the same contract more declaratively and return structured paths for nested failures.

## Syntax Is Necessary but Insufficient

This address is syntactically plausible:

```text
alice@example.com
```

But syntactic validation cannot tell whether the mailbox exists, belongs to Alice, or is already registered. Those are semantic questions.

Likewise, `2026-12-01` may match the required format but still be disallowed because a booking window ends in November.

## Building the Rules One Step at a Time

Suppose I am building a simple registration endpoint:

```http
POST /api/users
```

At first, I might only check whether `name` exists:

```js
if (!req.body.name) {
  return res.status(400).json({ message: "Name is required" });
}
```

That is a beginning, but it leaves many questions unanswered.

Can the name be a number? Can it contain 50,000 characters? What if it is only spaces? What happens if the body is an array instead of an object?

A complete syntactic contract grows in layers:

```text
Step 1: Body must be an object
Step 2: Name must be present
Step 3: Name must be a string
Step 4: Trim outer whitespace
Step 5: Name must contain 1–80 characters after trimming
Step 6: Reject fields the endpoint does not accept
```

This is how validation becomes more than one `if` statement. Every rule removes another ambiguity.

### Valid Request

```json
{
  "name": "Amina Yusuf",
  "email": "amina@example.com"
}
```

### Missing Required Field

```json
{
  "name": "Amina Yusuf"
}
```

The backend can respond:

```json
{
  "errors": [
    {
      "field": "email",
      "code": "required",
      "message": "Email is required."
    }
  ]
}
```

### Unexpected Field

```json
{
  "name": "Amina Yusuf",
  "email": "amina@example.com",
  "isAdmin": true
}
```

The backend should not assume that a field is safe because the database happens to contain a column with the same name. The public registration contract never offered `isAdmin`, so the field should not reach persistence.

## Why Email Regex Is Not the Whole Story

Beginners often meet validation through one example:

```js
const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
```

This can catch obvious mistakes such as missing `@` or a missing domain section. But it cannot prove that the mailbox exists or belongs to the user.

The complete email journey may be:

```text
Syntactic check → Does it resemble an accepted email address?
Normalization → Which spaces or casing rules do we apply?
Uniqueness check → Is another account already using it?
Verification email → Does the user control the mailbox?
```

One regex cannot answer four different questions.

## Checkpoint Questions

### What does syntactic validation check?

It checks the request's shape and format: required fields, known fields, lengths, patterns, nested objects, and array structure.

### Is an email valid just because it matches a regex?

No. A format check only shows that it resembles the accepted syntax. It does not prove that the address exists, is owned by the user, or is available for registration.

### Why should an API limit string and array sizes?

Limits protect storage, memory, database work, and downstream interfaces. A value can have the right type and still be dangerously large.

### What should happen to unknown fields?

The API needs an explicit policy. Public write endpoints commonly reject them or construct an allowlisted object so unexpected fields never reach business logic or persistence.

## What I Learned

Syntactic validation protects the structural boundary:

```text
shape
presence
format
length
nesting
allowed fields
```

It ensures that data looks like the documented language of the API. Part 5 goes one level deeper and checks whether every value has the correct runtime type.
