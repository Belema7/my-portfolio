# Syntactic Validation: Does the Data Look Correct?

> *“A request should say exactly what the contract allows—no less and no more.”*

## Introduction

Part 3 separated syntax, runtime type, and meaning. Now I want to slow down at the first gate:

> **Does the data have the shape and visible format this operation accepts?**

I used to reduce this question to “does the email match a regex?” Syntactic validation is much wider.

## Start With the Whole Shape

A Create User body should be a plain object, not an array, string, or `null`.

```ts
import { z } from "zod";

const createUserShape = z
  .object({
    name: z.string().min(1).max(80),
    email: z.email().max(254),
    age: z.unknown(),
  })
  .strict();
```

Zod 4.3.6 is installed in this repository's dependency tree, so these examples use its top-level `z.email()` API. The complete schema comes in Part 8.

Required fields answer “must this property exist?” Optional and nullable are different:

```text
missing       → property not supplied
undefined     → JavaScript value, not valid JSON
null          → supplied explicit empty value
""            → supplied empty string
```

The contract must decide each case intentionally.

## Strings, Formats, and Limits

A string rule usually needs more than `typeof value === "string"`:

- trim policy;
- minimum and maximum length;
- whether whitespace-only text counts;
- accepted Unicode;
- documented format.

Email validation can reject `belema@`. It cannot prove the inbox exists or belongs to the user.

Phone and URL rules also need product-specific contracts. Phone numbers should usually be parsed by a capable library and stored in a canonical form. A syntactically valid URL is not automatically safe for a redirect or server-side fetch.

## Arrays and Nested Objects

Nested input needs limits at every level.

```ts
const addressSchema = z
  .object({
    street: z.string().trim().min(1).max(120),
    city: z.string().trim().min(1).max(80),
  })
  .strict();

const tagsSchema = z
  .array(z.string().trim().min(1).max(30))
  .max(10);
```

Checking only “is array” misses element types and length. Checking only “is object” misses required nested properties and unknown keys. Deep nesting also consumes parsing work, so global nesting and body-size limits matter in production.

## Unknown Fields Are a Security Decision

Our caller supplied:

```json
{ "role": "admin" }
```

The registration contract does not accept `role`. Two defensible policies exist:

```text
Strict rejection → tell the client the field is unsupported.
Explicit stripping → ignore it according to a documented policy.
```

For this series I choose strict rejection because it exposes broken or suspicious clients. Whichever policy I choose, I must never spread the raw body into persistence.

This prevents mass assignment:

```ts
// Dangerous
database.user.create({ data: req.body });

// Explicit allowlist
database.user.create({
  data: {
    name: command.name,
    email: command.email,
    age: command.age,
  },
});
```

An allowlist remains safe when the database later gains `role` or `isVerified`.

## Errors Should Help Without Leaking

“Invalid request” is safe but frustrating. A field-level response can be both safe and useful:

```json
{
  "type": "validation_error",
  "message": "The request contains invalid fields.",
  "errors": [
    {
      "field": "email",
      "code": "invalid_format",
      "message": "Enter a valid email address."
    },
    {
      "field": "role",
      "code": "unrecognized_key",
      "message": "This field is not accepted."
    }
  ]
}
```

Stable codes help clients translate messages. Field paths help forms focus the correct input. Responses should not include stack traces, SQL, secrets, or the complete payload.

## Basic Rule vs Production Concern

| Basic rule | Production concern |
| --- | --- |
| Name is non-empty | Limit length and define whitespace/Unicode policy |
| Email matches format | Do not claim existence; normalize consistently |
| Body is an object | Reject arrays, `null`, unknown keys, deep nesting |
| Tags are strings | Limit array and element sizes |
| URL parses | Apply destination-specific allowlists later |

That was another realization: validation is not one giant regex. It is a precise public contract with resource limits.

## Presence, Empty, Null, and Whitespace

These inputs are different:

```json
{}
{ "name": null }
{ "name": "" }
{ "name": "   " }
```

A rule such as `z.string().trim().min(1).max(100)` defines their outcomes. Missing and `null` fail presence/type; empty and whitespace-only fail the post-trim length rule.

## Regex Is Not Understanding

Email syntax cannot prove deliverability, ownership, or uniqueness. A practical email policy combines reasonable syntax, maximum size, consistent normalization, verification for ownership, and a database constraint for uniqueness.

Trying to encode all of that in one “perfect” regex produces false confidence.

## Unicode and Length

JavaScript string length counts UTF-16 code units, not always user-perceived characters. Emoji and combining marks complicate UI counters and storage limits.

The API, database, and frontend should agree on practical limits and test representative Unicode. Normalization may be appropriate for identifiers, but silently changing user-authored display text requires a real product rule.

## Depth and Complexity Limits

Checking only “is object” misses nested keys. Checking only “is array” misses item types and item count. Deeply nested or enormous valid data can exhaust resources.

A production contract bounds:

- body size;
- object keys and unknown fields;
- array count;
- element size and shape;
- nesting complexity where relevant.

## Error Paths for Nested Fields

```json
{
  "code": "VALIDATION_FAILED",
  "fields": {
    "address.countryCode": ["Use a supported country code"],
    "items.2.quantity": ["Quantity must be at least 1"]
  }
}
```

The response identifies the field without echoing passwords, tokens, file contents, or the entire rejected payload.

## Boundary Test Matrix

For each field I test missing, `null`, empty, whitespace-only, one below minimum, exact minimum, exact maximum, one above maximum, malformed syntax, representative Unicode, and an unknown neighboring field.

These cases expose off-by-one errors and undocumented coercion better than many ordinary happy-path examples.

## Complete Syntactic Schema Example

```ts
const addressSchema = z.object({
  line1: z.string().trim().min(1).max(120),
  line2: z.string().trim().max(120).optional(),
  city: z.string().trim().min(1).max(80),
  countryCode: z.string().regex(/^[A-Z]{2}$/),
}).strict();

const createOrderSchema = z.object({
  reference: z.string().trim().min(1).max(40),
  shippingAddress: addressSchema,
  items: z.array(z.object({
    productId: z.string().uuid(),
    quantity: z.number().int().min(1).max(100),
  }).strict()).min(1).max(50),
}).strict();
```

This schema bounds the whole shape, nested objects, collection count, each item, and unknown keys. It still does not prove products exist, stock is available, or the country can receive shipping.

## Format Validation Is Policy

A phone-number field illustrates why regex examples are not universal. International numbers vary, users include spacing and prefixes, and the application may need a canonical E.164 representation.

The contract should define accepted external representations and use a domain-appropriate parser rather than copy a US-only `XXX-XXX-XXXX` regex into a global product.

URLs also need context. General URL syntax validation does not prove an avatar URL uses an allowed scheme or that a server-side fetch is safe from SSRF.

## Schema Error Stability

Validation libraries expose detailed internal issue codes. Public APIs should map them into stable application codes so a library upgrade does not silently break client behavior.

```text
library too_small → API min_length
library invalid_type → API invalid_type
library unrecognized_keys → API unknown_field
```

The public field path, code, and safe message form the contract.

## Avoid Over-Sanitizing User Text

Removing punctuation, accents, or non-Latin characters from names may damage legitimate data without improving security. SQL safety comes from parameterization; HTML safety comes from output encoding.

Syntax validation should enforce actual product constraints, not convert diverse human input into a narrow developer assumption.

## Checkpoint Questions

### 1. Why reject `role` even if it has a valid string value?

Because the field itself is outside this operation's contract. Validating its value would accidentally treat privileged assignment as public functionality.

### 2. What can email syntax validation prove?

Only that text follows an accepted format. It cannot prove existence, ownership, deliverability, or uniqueness.

### 3. Why validate array length as well as element shape?

Correct elements can still form an oversized request that wastes memory or creates expensive database work.
