# Backend from First Principles — Day 6 (Part 8)

# The Complete Validation Pipeline in Code

> *“The goal of a validation pipeline is not merely to reject bad input. It is to hand the service a small, trustworthy command.”*

---

## Introduction

Throughout Day 6, I have been learning one piece at a time.

I learned why client data is untrusted. I learned the difference between syntax, type, and meaning. I learned why query parameters sometimes need transformation. I also learned that controllers, services, and repositories protect different kinds of rules.

At first, these ideas felt separate.

Now I want to follow one request through the entire application and see where every piece fits.

The scenario is simple:

> **A user wants to create an account.**

The client sends a name, email, and optional age. The backend must turn that unknown JSON into a safe database record without trusting any step by accident.

The ideas from the previous parts become most useful when they form one predictable request pipeline:

```text
Extract
→ parse and transform
→ validate request contract
→ authenticate and authorize
→ enforce business invariants
→ persist safely
→ map result to HTTP
```

This part uses Express-style JavaScript and Zod-style schemas to show the architecture. The principles apply equally to Joi, Valibot, Yup, class-validator, Pydantic, Jakarta Bean Validation, or a carefully written custom validator.

## Before the Code: What Are Express and Zod Doing?

If I am new to backend development, the library names can distract from the lesson.

**Express** is a Node.js web framework. It receives HTTP requests and lets us connect routes to controller functions.

```js
app.post("/api/users", createUserController);
```

This means:

```text
When a POST request reaches /api/users,
run createUserController.
```

**Zod** is a runtime schema validation library. It lets us describe accepted data and then check an unknown value against that description.

```js
const nameSchema = z.string().min(1).max(80);
```

This means:

```text
The value must be a string.
It must contain at least 1 character.
It must contain no more than 80 characters.
```

The library syntax is useful, but the architecture matters more. Another language or framework can perform the same steps.

## 1. Define the Public Contract

```js
import { z } from "zod";

const createUserBodySchema = z
  .object({
    name: z.string().trim().min(1).max(80),
    email: z.string().trim().toLowerCase().email().max(254),
    age: z.number().int().min(0).max(150).optional(),
  })
  .strict();

const createUserRequestSchema = z.object({
  body: createUserBodySchema,
  requestId: z.string().min(1),
});
```

The strict body rejects unknown properties such as `role` or `isAdmin`. The schema accepts a JSON number for `age`; it does not silently coerce a string.

### Reading the Schema Like English

This code can look dense at first:

```js
name: z.string().trim().min(1).max(80)
```

Read it from left to right:

```text
name must be text
→ remove outer spaces
→ it cannot be empty afterward
→ it cannot exceed 80 characters
```

Now read the whole body contract:

```text
name is required
email is required and must have an email format
age may be absent, but if present it must be an integer from 0 to 150
no other fields are accepted
```

That is the public promise of `POST /api/users`.

That policy is different for query parameters, where text parsing is expected:

```js
const positiveIntegerText = z
  .string()
  .regex(/^\d+$/)
  .transform(Number)
  .refine(Number.isSafeInteger);

const listUsersQuerySchema = z
  .object({
    page: positiveIntegerText.pipe(z.number().min(1)).default("1"),
    limit: positiveIntegerText.pipe(z.number().min(1).max(100)).default("20"),
  })
  .strict();
```

Defaults apply only when a field is absent. A malformed value still fails.

## 2. Parse at the Boundary

```js
async function createUserController(req, res, next) {
  try {
    const parsed = createUserRequestSchema.safeParse({
      body: req.body,
      requestId: req.id,
    });

    if (!parsed.success) {
      return res.status(400).json(formatValidationErrors(parsed.error));
    }

    const user = await userService.register(parsed.data.body);

    return res.status(201).json({
      id: user.id,
      name: user.name,
      email: user.email,
    });
  } catch (error) {
    return next(error);
  }
}
```

The controller passes only the validated body to the service. It also shapes the response explicitly so internal fields such as password hashes never leak through serialization.

### What Does `safeParse` Return?

The parser has two possible outcomes.

Success:

```js
{
  success: true,
  data: {
    body: {
      name: "Amina",
      email: "amina@example.com",
      age: 24
    }
  }
}
```

Failure:

```js
{
  success: false,
  error: /* structured validation details */
}
```

The controller does not continue when parsing fails. That early return is the gate:

```text
Invalid request → 400 response → service is never called
Valid request → trusted data → service is called
```

## 3. Enforce Semantic Rules in the Service

```js
async function register(input) {
  const existing = await userRepository.findByEmail(input.email);

  if (existing) {
    throw new EmailConflictError();
  }

  try {
    return await userRepository.create(input);
  } catch (error) {
    if (isUniqueEmailViolation(error)) {
      throw new EmailConflictError();
    }

    throw error;
  }
}
```

The service performs a friendly pre-check. It also handles the database unique constraint because concurrency can defeat a check-then-insert sequence.

The database remains authoritative for uniqueness.

### Why Is Email Uniqueness Not in the Basic Schema?

The schema can examine the request value by itself. It can tell whether the email is a string and whether it has an accepted format.

It cannot know whether another user registered the same email one millisecond ago. That information lives in current application state.

The service asks the repository, and the database unique constraint provides the final safety net.

## 4. Persist an Explicit Object

```js
async function create(input) {
  return database.user.create({
    data: {
      name: input.name,
      email: input.email,
      age: input.age ?? null,
    },
    select: {
      id: true,
      name: true,
      email: true,
      age: true,
    },
  });
}
```

Explicit mapping is safer than spreading `req.body` into a persistence call:

```js
// Dangerous boundary design
database.user.create({ data: req.body });
```

Allowlisting protects against accidental fields, privilege fields, and future schema changes.

### The Dangerous Spread Operator

This pattern is tempting:

```js
data: { ...req.body }
```

It means “copy everything the client sent.” That gives the client influence over fields the developer may never have intended to expose.

Explicit mapping says:

```text
The public request may control name, email, and age.
Nothing else crosses this boundary.
```

Writing three lines instead of one can be an important security decision.

## 5. Return Structured Validation Errors

```js
function formatValidationErrors(error) {
  return {
    type: "validation_error",
    message: "The request contains invalid fields.",
    errors: error.issues.map((issue) => ({
      field: issue.path.join("."),
      code: issue.code,
      message: issue.message,
    })),
  };
}
```

Example response:

```json
{
  "type": "validation_error",
  "message": "The request contains invalid fields.",
  "errors": [
    {
      "field": "body.email",
      "code": "invalid_format",
      "message": "Invalid email address"
    }
  ]
}
```

In a mature API, public error codes should remain stable even if the underlying library changes. A mapping layer can translate library-specific issue codes into the API’s own vocabulary.

## 6. Map Domain Errors Separately

```js
function errorHandler(error, req, res, next) {
  if (error instanceof EmailConflictError) {
    return res.status(409).json({
      type: "conflict",
      code: "email_already_registered",
      message: "An account already uses that email.",
    });
  }

  req.log.error({ error, requestId: req.id }, "Unhandled request error");

  return res.status(500).json({
    type: "server_error",
    message: "An unexpected error occurred.",
    requestId: req.id,
  });
}
```

Validation failures, conflicts, authorization failures, and server failures are different categories. A global error mapper keeps the distinction consistent.

## Middleware Ordering

A typical route stack might be:

```js
app.post(
  "/api/users",
  requestIdMiddleware,
  bodySizeLimit,
  express.json(),
  rateLimitRegistration,
  createUserController,
);
```

For a protected route:

```js
app.patch(
  "/api/teams/:teamId/members/:memberId",
  authenticate,
  validateChangeRoleRequest,
  authorizeTeamAdmin,
  changeMemberRoleController,
);
```

The precise order depends on cost and information needs. Size limits should run before expensive parsing. Authentication may run before or after cheap structural validation depending on whether the endpoint wants to reveal validation details to anonymous callers. Authorization must use validated identifiers and trusted identity.

### What Is Middleware?

Middleware is code that runs during the request journey before or after the final controller.

Imagine airport checkpoints:

```text
Entrance → Ticket check → Security scan → Passport check → Boarding gate
```

Each checkpoint handles one responsibility. If a check fails, the passenger does not continue.

A backend request can move similarly:

```text
Request ID → Size limit → JSON parser → Rate limit → Authentication → Validation → Controller
```

The order matters. There is no reason to parse a gigantic body before checking the configured size limit.

## Test Each Stage

At minimum, tests should cover:

- missing and unknown fields;
- wrong primitive types;
- boundary values and over-limit values;
- invalid nested arrays or objects;
- normalization behavior;
- semantic conflicts;
- concurrent uniqueness enforcement;
- safe public errors;
- absence of internal fields in responses.

Property-based or fuzz testing can add malformed shapes humans may not think to write manually.

## The Entire Request in One Picture

```text
POST /api/users
        ↓
Body-size middleware
“Is this request small enough to process?”
        ↓
JSON parser
“Can this text become JSON?”
        ↓
Request schema
“Does it match the public contract?”
        ↓
Controller
“Create a small trusted command.”
        ↓
User service
“Does this operation make business sense?”
        ↓
Repository
“Perform the required database operation.”
        ↓
Database constraints
“Protect final storage invariants.”
        ↓
Explicit response
“Return only public fields.”
```

## Checkpoint Questions

### What happens when `safeParse` fails?

The controller returns a validation response and does not call the service. Invalid input is rejected at the boundary.

### Why does the controller return an explicit response object?

Database records may contain internal or sensitive fields. Explicit response mapping ensures only the API's public fields are serialized.

### Why does the service catch a database uniqueness violation after checking email first?

The first check gives a friendly result in the common case. The database violation handles concurrent requests and remains the authoritative guarantee.

### What is the main purpose of the whole pipeline?

To turn a large, unknown HTTP request into a small, trustworthy command before significant business work begins.

The complete flow is:

```text
Raw request
→ validated request DTO

→ protected domain operation
→ constrained persistence

```
