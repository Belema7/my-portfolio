# Implementing the Boundary with Zod and TypeScript

> *“Runtime validation earns the TypeScript type that deeper code is allowed to trust.”*

## Introduction

By Part 7, my rules were clear. But manually repeating `if` statements would make the contract scattered and difficult to reuse.

> **How do I turn these rules into code without creating hundreds of manual checks?**

This repository resolves Zod **4.3.6** in its installed dependency tree. The example therefore uses supported Zod 4 APIs: `z.strictObject`, top-level `z.email()`, `safeParse`, transforms, and inferred output types.

## One Complete Boundary

```ts
import { z } from "zod";

const ageFromRequest = z
  .union([z.string(), z.number()])
  .transform((value, context) => {
    const age =
      typeof value === "number"
        ? value
        : /^\d+$/.test(value)
          ? Number(value)
          : Number.NaN;

    if (!Number.isSafeInteger(age)) {
      context.addIssue({
        code: "custom",
        message: "Age must be a whole number.",
      });
      return z.NEVER;
    }

    return age;
  })
  .pipe(z.number().int().min(0).max(150));

export const createUserSchema = z.strictObject({
  name: z.string().trim().min(1).max(80),
  email: z
    .string()
    .trim()
    .toLowerCase()
    .pipe(z.email().max(254)),
  age: ageFromRequest,
});

export type CreateUserCommand =
  z.output<typeof createUserSchema>;
```

Read it as:

```text
name  → string → trim → length
email → string → trim → lowercase → format and length
age   → documented string/number → strict integer → range
body  → only known keys
```

The input type and output type are not identical. Age may enter as digit text, but successful parsing always produces a number.

## Why `safeParse` Fits a Boundary

```ts
type PublicFieldError = {
  field: string;
  code: string;
  message: string;
};

function parseCreateUserBody(body: unknown):
  | { ok: true; command: CreateUserCommand }
  | { ok: false; errors: PublicFieldError[] } {
  const result = createUserSchema.safeParse(body);

  if (!result.success) {
    return {
      ok: false,
      errors: result.error.issues.map((issue) => ({
        field: issue.path.join(".") || "body",
        code: issue.code,
        message: issue.message,
      })),
    };
  }

  return { ok: true, command: result.data };
}
```

`safeParse` turns expected invalid input into an explicit branch. Unexpected bugs still throw and follow normal error handling.

## Controller Helper and Typed Handoff

```ts
async function createUserController(
  req: Request,
  res: Response,
) {
  const parsed = parseCreateUserBody(req.body);

  if (!parsed.ok) {
    return res.status(400).json({
      type: "validation_error",
      message: "The request contains invalid fields.",
      errors: parsed.errors,
    });
  }

  const user = await userService.createUser(
    parsed.command,
    req.auth.actor,
  );

  return res.status(201).json({
    id: user.id,
    name: user.name,
    email: user.email,
    age: user.age,
  });
}
```

The controller knows HTTP. The service receives `CreateUserCommand`, not `Request`.

```ts
async function createUser(
  command: CreateUserCommand,
  actor: Actor,
) {
  assertCanCreateUsers(actor);
  await assertEmailAvailable(command.email);
  return userRepository.create(command);
}
```

The schema does not hide permission or database queries. Those are business rules.

## Unknown Fields and the Recurring Request

With a strict object, this request fails because `role` is unrecognized:

```json
{
  "name": " Belema ",
  "email": "BELEMA@EMAIL.COM",
  "age": "21",
  "role": "admin"
}
```

If the client removes `role`, successful output becomes:

```ts
{
  name: "Belema",
  email: "belema@email.com",
  age: 21,
}
```

That TypeScript type was earned through runtime parsing. It was not asserted.

## Middleware or Controller Helper?

Either can represent the boundary. Middleware can attach validated data for several controllers; a helper can keep flow explicit and local. NestJS may use a DTO and validation pipe.

The choice matters less than these guarantees:

- raw data is typed as unknown at entry;
- the schema executes at runtime;
- failures stop before the service;
- success produces a narrow command;
- services still enforce business meaning.

## Input and Output Types Can Differ

Zod transformations have an input type and an output type:

```ts
const pageSchema = z
  .string()
  .regex(/^[1-9]\d*$/)
  .transform(Number)
  .pipe(z.number().int().max(10_000));

type RawPage = z.input<typeof pageSchema>;   // string
type Page = z.output<typeof pageSchema>;     // number
```

The service needs `Page`, not the raw representation. This is why `z.output` communicates the post-transformation guarantee.

## Preprocess Versus Coerce Versus Transform

Broad coercion such as `z.coerce.boolean()` can inherit surprising JavaScript truthiness. Explicit preprocessing or transformation is safer when only a narrow grammar is accepted.

```ts
const queryBooleanSchema = z.union([
  z.literal("true").transform(() => true),
  z.literal("false").transform(() => false),
]);
```

The schema documents exactly which external values exist.

## Reusable Schemas Without One Giant Schema

Small field schemas can be composed:

```ts
const emailSchema = z.string().trim().toLowerCase().email().max(254);
const displayNameSchema = z.string().trim().min(1).max(100);

const createUserSchema = z.object({
  name: displayNameSchema,
  email: emailSchema,
  password: passwordSchema,
}).strict();
```

But operations still need distinct object schemas. Extending a stored `UserSchema` and omitting a few fields can accidentally inherit rules inappropriate for a public request.

## Async Refinements Need Care

Zod can run async refinements, but putting database uniqueness inside a schema mixes a changing business rule with a representation contract.

Use async refinements for boundary concerns only when their ownership and failure behavior are clear. Network or database outages should not be mislabeled as “invalid email.”

## A Typed Middleware Handoff

```ts
function validateBody<TSchema extends z.ZodTypeAny>(schema: TSchema) {
  return (req: Request, res: Response, next: NextFunction) => {
    const result = schema.safeParse(req.body);
    if (!result.success) return sendValidationError(res, result.error);

    req.validatedBody = result.data;
    next();
  };
}
```

TypeScript cannot automatically prove every handler was registered after this middleware. Route composition and integration tests must support the runtime guarantee. Some projects prefer a local `parseBody(schema, req)` helper because the data flow stays explicit.

## Schema Versioning

Tightening a schema can break old clients. Adding a required field, rejecting previously stripped keys, or changing coercion is an API contract change.

Versioned endpoints, transition periods, metrics on rejected fields, and coordinated client releases may be needed. Runtime schemas are executable API specifications, so changes deserve review.

## Error Design

Zod's internal issue codes are useful, but a public API may map them to stable application codes. Changing libraries should not silently change the client contract.

The response should expose field, stable code, and safe message. It should not expose stack traces or the entire submitted payload.

## Boundary Tests for the Schema

```text
valid canonical body
valid body requiring normalization
missing field
null field
wrong runtime type
unknown role field
overlong strings
age boundaries
malformed query representations
multiple simultaneous field errors
```

The test should assert both rejection and the exact parsed output handed to the service.

## Complete Route Composition

```ts
const validateCreateUser = validateBody(createUserSchema);

router.post(
  "/users",
  requestIdMiddleware,
  createUserRateLimiter,
  validateCreateUser,
  createUserHandler,
);
```

The effective order is part of correctness. Rate limiting protects expensive work. Validation prevents malformed input from reaching the handler/service. The handler consumes the parsed output, not `req.body`.

## Mapping Zod Issues

```ts
function mapIssues(error: z.ZodError) {
  return error.issues.map((issue) => ({
    field: issue.path.join(".") || "body",
    code: mapIssueCode(issue.code),
    message: safeIssueMessage(issue),
  }));
}
```

The mapper stabilizes the public contract. It should avoid including rejected secret values or schema internals clients do not need.

## Type Inference Without Type Leakage

```ts
type CreateUserCommand = z.output<typeof createUserSchema>;
```

This can prevent schema/type drift. In larger architectures, the application command may be declared independently and the adapter maps schema output into it so the service does not import Zod at all.

Both designs are valid if runtime proof and dependency direction remain clear.

## Refinement Ordering

Transformations and refinements execute in library-defined order. A trim, lowercase, format check, and custom refinement can behave differently depending on composition.

Tests should prove the exact accepted raw values and output, especially after upgrading Zod. The project instruction to read installed-version documentation matters because schema APIs and behavior evolve.

## Error Localization

Stable codes belong in the API. Human messages may be localized by the frontend or server according to product design. Clients should not branch on English text.

```json
{
  "field": "email",
  "code": "invalid_format",
  "message": "Enter a valid email address."
}
```

## Schema Performance

Deep unions, large arrays, and expensive refinements can consume CPU. Body and collection limits should run before or alongside schema validation. Benchmarking matters for hot or adversarial endpoints.

Validation libraries reduce boilerplate; they do not eliminate resource engineering.

## Checkpoint Questions

### 1. Why use `z.output` for the service command?

Because transformations can make the parsed output different from raw input. The service needs the guaranteed post-transformation type.

### 2. Why keep uniqueness out of this schema?

Uniqueness depends on changing database state and belongs to the business operation, backed by a database constraint.

### 3. What does strict object parsing protect?

It rejects unknown fields, exposes contract drift, and helps prevent over-posting such as public `role` assignment.
