# The Journey of Data and the Application Boundary

> *“Raw requests stop at the boundary. Business logic receives an explicit command.”*

## Introduction

Part 1 taught me why every client is outside the trust boundary. That created a new question:

> **Where should raw request data be inspected before it reaches business logic?**

I first answered, “inside the controller.” That was too narrow. Frameworks use different mechanisms, and deeper layers protect different truths.

## The Layered Picture

```text
Client
   ↓
Request Boundary
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

Each stage answers something different:

```text
Boundary:   Does this request satisfy the public contract?
Controller: Which HTTP response represents the result?
Service:    Is this operation allowed and meaningful now?
Repository: How is the persistence operation performed?
Database:   Which stored facts must always remain true?
```

This separation stops uncertainty from spreading.

## Input Is More Than `req.body`

An HTTP caller can influence:

- request bodies;
- query parameters;
- path parameters;
- selected headers;
- cookies;
- uploaded files;
- the raw token or session used to establish authentication context.

Verified authentication context is more trustworthy than a body field like `userId` because server middleware established it. But the service must still check ownership and permission for this operation.

## Extract, Transform, Validate

The request boundary performs a deliberate pipeline:

```text
Extract → Transform → Validate
```

Our request is:

```json
{
  "name": " Belema ",
  "email": "BELEMA@EMAIL.COM",
  "age": "21",
  "role": "admin"
}
```

Extraction chooses only fields this operation accepts. Transformation converts documented external representations. Validation proves the public request contract.

```ts
const candidate = {
  name: req.body?.name,
  email: req.body?.email,
  age: req.body?.age,
};
```

The schema must still verify that the body is an object and enforce its unknown-field policy. Explicit mapping is an allowlist, not complete validation.

## Why Passing the Whole Body Is Dangerous

```ts
await userService.createUser(req.body);
```

This couples business logic to an open-ended HTTP object. Worse, code may later spread it into an ORM:

```ts
await database.user.create({ data: req.body });
```

If the model contains `role`, `isVerified`, or `balance`, callers may assign fields the operation never exposed. This is a mass-assignment risk.

The safer handoff is narrow:

```ts
type CreateUserCommand = {
  name: string;
  email: string;
  age: number;
};

await userService.createUser(validatedCommand);
```

Adding a database column does not silently add an API feature.

## Controller, Service, Repository, Database

The controller handles HTTP: it receives validated data, calls a service, shapes a response, and maps expected errors to status codes.

The service applies business rules: permissions, ownership, existence, uniqueness, state transitions, and orchestration. Services do validate—just not raw HTTP representations.

The repository performs persistence operations. It should not parse query strings or return HTTP responses.

The database enforces stored truth with unique indexes, foreign keys, check constraints, transactions, and atomic operations.

```text
Request-contract validation → boundary
Business validation         → service
Stored-data invariants      → database
```

## One Boundary, Different Framework Shapes

Express may use body-limit middleware, authentication middleware, a schema parser, and a controller helper.

NestJS may use guards, DTOs, and validation/transformation pipes before the controller method.

Validation does not have to live in one physical file. The accurate principle is:

> **Request-contract validation happens at the application boundary before business logic.**

## Boundary Rules and Business Rules

The statement “validate before the service” applies to request representation. It does not mean the service protects no rules.

```text
Request boundary
  Is email a bounded string with accepted syntax?
  Is age a runtime integer?
  Are unknown fields forbidden?

Service
  Is registration open?
  May this actor assign this role?
  Is the invitation valid for this email?

Database
  Is normalized email unique at commit time?
  Does the foreign key remain valid?
```

All are sometimes called validation, but they establish different guarantees.

## Explicit Command Construction

```ts
const parsed = createUserSchema.parse(req.body);

const command: CreateUserCommand = {
  name: parsed.name,
  email: parsed.email,
  password: parsed.password,
  age: parsed.age,
};
```

The command has no `role`, `id`, `isVerified`, or `passwordHash`. Explicit mapping documents what the service is allowed to receive and prevents future database columns from becoming API features accidentally.

## Reject Cheaply Before Expensive Work

Defense is strongest when inexpensive checks reject invalid work early:

```text
network/proxy body limit
  ↓
parser body limit
  ↓
shape and type validation
  ↓
identity and permission checks
  ↓
stateful database rules
  ↓
persistence
```

Exact order depends on the endpoint, but there is no reason to query whether `not-an-email` is unique.

## Other Adapters Need Boundaries Too

A queue consumer does not go through an Express controller:

```ts
async function consumeImport(message: unknown) {
  const command = importUserMessageSchema.parse(message);
  await createUserService.execute(command);
}
```

The consumer is another application boundary. This explains why critical business rules remain inside the service even when HTTP input was already validated.

## Output Is Also a Boundary

```ts
function toUserResponse(user: User) {
  return {
    id: user.id,
    name: user.name,
    email: user.email,
    createdAt: user.createdAt.toISOString(),
  };
}
```

A database record may contain password hashes, tokens, risk flags, and storage naming. The public response should allowlist safe fields rather than serialize internal data directly.

## Guarantees at Every Handoff

| Handoff | Guarantee |
| --- | --- |
| Parser → boundary | representation became a runtime value |
| Boundary → service | shape, type, and transformations proven |
| Service → repository | business operation accepted |
| Repository → database | destination-safe query and mapping |
| Database → application | stored constraints enforced |
| Handler → client | public fields only |

## Complete Create User Boundary Example

```ts
const createUserSchema = z.object({
  name: z.string().trim().min(1).max(100),
  email: z.string().trim().toLowerCase().email().max(254),
  password: z.string().min(12).max(128),
  age: z.number().int().min(0).max(150).optional(),
}).strict();

async function createUserHandler(req: Request, res: Response, next: NextFunction) {
  try {
    const parsed = createUserSchema.safeParse(req.body);

    if (!parsed.success) {
      return res.status(400).json({
        error: {
          code: "VALIDATION_FAILED",
          fields: mapIssues(parsed.error.issues),
        },
      });
    }

    const command: CreateUserCommand = {
      name: parsed.data.name,
      email: parsed.data.email,
      password: parsed.data.password,
      age: parsed.data.age,
    };

    const user = await createUserService.execute(command);
    res.status(201).json({ user: toUserResponse(user) });
  } catch (error) {
    next(error);
  }
}
```

The handler exposes the application boundary clearly. Raw `req.body` never reaches the service.

## What if Validation Lives in Middleware?

```ts
router.post(
  "/users",
  validateBody(createUserSchema),
  createUserHandler,
);
```

This can reduce repeated parsing code, but it introduces an ordering contract: the handler must only run after validation. The validated property needs an honest TypeScript type, and integration tests must prove route composition.

Neither middleware nor local helper is universally better. The guarantee matters:

```text
failure stops before business logic
success produces a narrow typed command
```

## Avoid Passing Validation-Library Objects Inward

The service should not depend on Zod issues or Express validation results. The boundary maps library output into the API's stable error format and passes only application data inward.

This keeps a future validation-library change from becoming a service rewrite.

## Boundary Performance Is Observable

Metrics can distinguish parser rejection, schema rejection, business conflict, and database failure. If a new mobile release suddenly increases `unknown_field` errors, the contract and client likely drifted.

Observability should record route templates and stable error codes, not rejected passwords, tokens, or entire request bodies.

## The Receptionist Analogy

I picture the boundary as a receptionist. Visitors do not wander into every office carrying unexamined folders. The receptionist checks the destination and required packet, then gives the department known information.

The department still decides whether the request is allowed. The records system still enforces filing rules.

## My Biggest Realization

I used to ask, “Where is the validation file?”

Now I ask, “Which guarantee belongs to which boundary?”

Raw requests must not drift into business logic. The boundary creates a command; the service decides meaning; the repository persists; the database protects stored truth.

## Checkpoint Questions

### 1. Why is `userService.createUser(req.body)` unsafe?

It sends an unknown, open-ended external object into business logic and can enable mass assignment. A validated command gives known fields and types.

### 2. Does all validation belong in a controller?

No. Middleware, schemas, DTOs, pipes, and controller helpers may enforce request contracts. Services enforce business rules, and databases enforce stored invariants.

### 3. What is a repository responsible for?

Persistence operations and database mapping—not HTTP request validation or hidden business workflows.
