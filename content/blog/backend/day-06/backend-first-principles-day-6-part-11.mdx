# Backend from First Principles — Day 6 (Part 11)

# Putting Validation and Transformation Together

> *“A trustworthy service does not receive raw requests. It receives an explicit command whose shape, representation, meaning, and authority have been established.”*

---

## Introduction

Day 6 began with a simple truth:

```text
The server does not control what clients send.
```

From that truth follows an entire architecture. The backend must limit input size, extract the intended fields, transform external representations carefully, validate shape and type, enforce business meaning, protect database invariants, and return consistent errors.

Validation and transformation are not isolated helper functions. They are the gatekeepers of data integrity.

## The Complete Request Flow

```text
1. Client sends untrusted input
        ↓
2. HTTP boundary applies protocol and size limits
        ↓
3. Controller extracts body, query, params, and selected headers
        ↓
4. Parser transforms documented external representations
        ↓
5. Boundary schema validates syntax and runtime types
        ↓
6. Authentication establishes trusted identity
        ↓
7. Authorization and service enforce semantic rules
        ↓
8. Repository and database protect persistence invariants
        ↓
9. Controller serializes an explicit response
```

The order can vary slightly by endpoint, but the responsibilities remain.

## The Three Validation Questions

### 1. Syntactic: Does It Look Right?

```text
required fields
known properties
string lengths
array sizes
nested shape
documented formats
```

### 2. Type: Is It Represented Correctly?

```text
string
finite number or integer
boolean
array with validated items
non-null object
explicit optionality and nullability
```

### 3. Semantic: Does It Make Sense Here?

```text
resource exists
value is unique
actor has permission
state transition is allowed
related fields agree
inventory or capacity is available
operation remains valid under concurrency
```

These questions move from surface structure to business truth.

## The Role of Transformation

Transformation turns one deliberate representation into another:

```text
query "20" → integer 20
query "false" → boolean false
external timestamp → validated internal time representation
spaced email → normalized comparison form
```

The rules are:

```text
Do not guess.
Do not rely on truthiness.
Do not accept partial parses.
Use defaults for absence, not malformed values.
Validate before and after conversion as needed.
```

## Layer Ownership

The mature model is more precise than “all validation belongs in the controller.”

| Layer | Owns |
| --- | --- |
| HTTP/controller boundary | Request shape, parsing policy, transport limits, HTTP errors |
| Service/domain | Business meaning, authorization, workflows, state transitions |
| Repository/database | Safe queries, transactions, uniqueness, references, atomic invariants |
| Response boundary | Explicit public shape, output encoding, sensitive-field exclusion |

This prevents raw HTTP details from spreading inward while ensuring critical rules cannot be bypassed by non-HTTP callers.

## The Golden Rules of Day 6

### Never Trust Client-Controlled Data

This includes authenticated clients and internal services. Authentication proves identity, not correctness.

### Validate on the Server

Frontend validation is valuable for usability but can always be bypassed.

### Treat Runtime Input as Unknown

Static types and type assertions do not inspect network payloads.

### Allowlist Accepted Fields

Build explicit command and persistence objects. Do not spread request bodies into database operations.

### Keep Parsing Strict

Exact conversions are easier to debug and safer than broad coercion.

### Bound Every Cost

Limit bodies, strings, arrays, files, pagination, nesting, and expensive processing.

### Protect Invariants at the Authoritative Layer

Use service rules, transactions, unique indexes, foreign keys, and atomic database operations where appropriate.

### Use Context-Specific Security Defenses

Validation does not replace parameterized SQL, output encoding, authorization, rate limiting, or secure file handling.

### Return Clear but Safe Errors

Use stable codes and field paths without leaking secrets or internal implementation details.

### Test Failure Paths

Boundaries, malformed shapes, races, and rejected state transitions deserve first-class tests.

## A Final Example

Imagine this request:

```http
POST /api/orders?notify=true
Authorization: Bearer <credential>
Content-Type: application/json

{
  "productId": "prod_42",
  "quantity": 2
}
```

The complete reasoning is:

```text
Protocol:
Is the body within the size limit and valid JSON?

Authentication:
Does the credential establish an active user?

Transformation:
Does query text "true" map exactly to boolean true?

Syntactic/type validation:
Is productId a permitted identifier string?
Is quantity an integer from 1 to 100?
Are unknown fields absent?

Authorization:
May this user order for the target account?

Semantic validation:
Does the product exist and may it be sold?
Is sufficient stock available?

Persistence:
Can stock decrement and order creation happen atomically?

Response:
Which order fields are safe and useful to return?
```

What looked like one request is really a chain of trust decisions.

## The Senior Engineer Mindset

A senior approach to validation is not about writing the most conditions. It is about asking the right boundary questions before failures reach production:

```text
What can the caller control?
What representation does the contract promise?
What is the maximum work this input can cause?
Which rule needs current state?
Which layer is authoritative under concurrency?
What information could this error leak?
How will the contract evolve without surprising clients?
```

This mindset treats invalid input as an expected part of operating an API, not an exceptional surprise.

## Day 6 Final Checklist

- Validate body, query, params, selected headers, cookies, and files as applicable.
- Distinguish syntax, type, and semantic rules.
- Normalize only where product semantics allow it.
- Reject ambiguous coercions and unknown write fields.
- Keep services independent from HTTP objects.
- Enforce business invariants in service or domain operations.
- Back concurrency-sensitive rules with database guarantees.
- Use explicit response objects and safe output handling.
- Keep errors consistent, actionable, and non-sensitive.
- Test missing, malformed, boundary, hostile, and concurrent inputs.

## Conclusion

The core lesson of Day 6 is simple:

> **Do not let raw requests become business data by accident. Make them earn trust through a deliberate pipeline.**

When the service receives clean, correctly typed, meaningful input, every deeper layer becomes easier to secure, test, and maintain. That is why validation and transformation are not small implementation details. They are the quality-control system for the entire API.
