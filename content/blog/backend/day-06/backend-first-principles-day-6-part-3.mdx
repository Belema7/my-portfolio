# Backend from First Principles — Day 6 (Part 3)

# What Validation Really Means

> *“Validation is checking whether incoming data is the data the operation expects.”*

---

## Introduction

So far, I have used the word **validation** many times.

But if someone asked me at the beginning of my backend journey, “What exactly are you validating?” I probably would have answered:

> “I check whether the input is correct.”

That answer is not wrong. It is just too vague.

Correct in which way?

Does the value have the correct format? Is it the correct JavaScript type? Does it follow the rules of the application? Those are different questions, and they can produce different answers.

This part gives me a simple mental model for separating them.

Validation is the process of deciding whether input satisfies an explicit contract.

That definition sounds simple, but “valid” has several meanings. The string may have a valid format while representing an impossible value. A number may have the right type but violate a business rule. An identifier may look correct but point to no existing resource.

I can make the subject clearer by dividing validation into three levels.

## The Three Levels

| Level | Checks | Main question |
| --- | --- | --- |
| Syntactic | Shape, required fields, length, pattern | Does it look right? |
| Type | String, number, boolean, array, object | Is it represented correctly? |
| Semantic | Meaning, state, permissions, relationships | Does it make sense here? |

Consider a booking date:

```json
{ "startDate": "2026-02-30" }
```

It is a string. It even resembles the `YYYY-MM-DD` pattern. But February 30 does not exist. If the date were real but already in the past, it could still fail the booking rule.

That produces three separate questions:

```text
Syntactic: does it match the accepted date representation?
Type/value: can it become a real date?
Semantic: is that date available and allowed for this booking?
```

## A School Registration Example

Imagine a student registration API receives this data:

```json
{
  "name": "Amina",
  "age": 12,
  "classId": "class_7"
}
```

Let us check it level by level.

### Level 1: Syntactic Validation

First, does the request have the shape we expect?

```text
Is name present?
Is age present?
Is classId present?
Is name shorter than the maximum length?
Does classId follow our identifier pattern?
```

At this stage, we are checking the structure of the message.

### Level 2: Type Validation

Next, are the values represented correctly?

```text
Is name a string?
Is age an integer?
Is classId a string?
```

The value `"12"` may look like an age to a human, but it is still a string. If the JSON contract requires a number, the backend should reject it or deliberately transform it according to a documented rule.

### Level 3: Semantic Validation

Finally, does the request make sense in the real application?

```text
Is age 12 accepted by this school?
Does class_7 actually exist?
Is class_7 already full?
Is this student already registered?
```

Now the backend needs business knowledge and perhaps database information.

One request passes through all three levels before the school can safely register the student.

## The Input Pipeline

A dependable pipeline looks like this:

```text
Raw request
  → extract selected sources
  → parse or transform according to policy
  → validate shape and primitive values
  → validate business meaning
  → create trusted command
  → call service operation
```

Some libraries combine parsing, coercion, and validation into one schema call. That is fine as long as the behavior is intentional and testable.

### What Does “Extract” Mean?

Extraction means selecting the data needed for this operation from the complete HTTP request.

Imagine this route:

```http
PATCH /teams/team_12/members/user_9?notify=true
```

The data is spread across the request:

```text
team_12     → path parameter
user_9      → path parameter
notify=true → query parameter
new role    → request body
actor ID    → authenticated identity
```

Extraction gathers the required values. Validation then checks them. The service should receive a deliberate object instead of searching through the request itself.

### What Does “Schema” Mean?

A schema is a written description of accepted data.

For example:

```text
name: required string, 1 to 80 characters
email: required string, valid email format
age: optional integer, 0 to 150
```

A validation library lets us describe that contract in code. The schema acts like a form the backend uses to inspect every request consistently.

For example, query parameters are text at the HTTP boundary:

```http
GET /reports?year=2026&includeDrafts=false
```

The API contract may parse those into:

```js
{ year: 2026, includeDrafts: false }
```

By contrast, a JSON body contract may require the client to send an actual boolean and reject the string `"false"`. Both policies can be correct. Consistency matters more than silent convenience.

## Validation Narrows Possibilities

Before validation, a value can be almost anything:

```js
unknown
```

After validation, the application has a narrower guarantee:

```ts
type CreateUserInput = {
  name: string;
  email: string;
  age?: number;
};
```

TypeScript alone cannot create that guarantee. Network input is runtime data, and static types do not validate it. Writing this is an assertion, not evidence:

```ts
const input = req.body as CreateUserInput;
```

A runtime schema or explicit checks must prove the claim.

### Think of a Funnel

Before validation, the input can be anything:

```text
number
string
array
null
an enormous object
missing fields
unexpected fields
```

Validation works like a funnel:

```text
Anything from the network
        ↓
Expected object only
        ↓
Expected fields only
        ↓
Expected types only
        ↓
Accepted values only
        ↓
Trusted input for this operation
```

Every stage removes possibilities until the application knows exactly what it is handling.

## Presence Is More Subtle Than Truthiness

This check is common:

```js
if (!data.quantity) {
  throw new Error("Quantity is required");
}
```

But truthiness combines several values:

```text
undefined, null, "", 0, false, NaN
```

Sometimes `0` and `false` are valid. A better contract distinguishes:

- missing;
- explicitly `null`;
- empty string;
- present but invalid;
- present and valid.

Precise validation produces precise API behavior.

### A Common Beginner Bug

Imagine an API for updating notification settings:

```js
if (!req.body.receiveEmails) {
  throw new Error("receiveEmails is required");
}
```

The user sends:

```json
{ "receiveEmails": false }
```

This is a valid choice. But `false` is falsy, so the code incorrectly says the field is missing.

The real question should be:

```js
if (req.body.receiveEmails === undefined) {
  throw new Error("receiveEmails is required");
}
```

This checks absence instead of truthiness.

## Failures Are Part of the Contract

A useful validation response tells the caller what can be corrected without exposing internal details:

```json
{
  "type": "validation_error",
  "message": "The request contains invalid fields.",
  "errors": [
    {
      "field": "email",
      "code": "invalid_format",
      "message": "Enter a valid email address."
    },
    {
      "field": "age",
      "code": "out_of_range",
      "message": "Age must be between 0 and 150."
    }
  ]
}
```

Machine-readable codes help clients localize or customize messages. Field paths help forms focus the correct input. A stable top-level shape helps every endpoint behave consistently.

However, errors should not echo secrets, stack traces, SQL, internal table names, or entire malicious payloads.

## Validation Is Not Sanitization

Validation asks whether data is allowed. Sanitization or normalization deliberately changes its representation. Output encoding makes data safe for a particular destination.

These should not be blurred:

```text
Validation: reject a display name longer than 80 characters.
Normalization: trim surrounding whitespace.
Parameterized SQL: keep input separate from query syntax.
HTML output encoding: render text without executing markup.
```

There is no universal `sanitize()` function that makes a value safe everywhere. Safety depends on the sink: SQL, HTML, shell commands, URLs, and logs each have different rules.

## Validate the Entire Request Surface

Teams often validate `req.body` and forget everything else. But all client-controlled sources deserve a contract:

```text
body
query parameters
path parameters
headers
cookies
file metadata and content
webhook payloads
message queue events
```

Even server-to-server traffic is not automatically trustworthy. Services can be misconfigured or compromised, and contracts can drift.

## The First Line of Defense, Not the Only One

Validation reduces risk, but it does not replace:

- authentication and authorization;
- parameterized database queries;
- output encoding;
- rate limits and size limits;
- database constraints;
- secure file handling;
- observability and auditing.

It is one layer in a defense-in-depth system.

## Checkpoint Questions

### What are the three levels of validation?

Syntactic validation checks structure and format. Type validation checks runtime representation. Semantic validation checks meaning and business context.

### Can a value pass syntactic validation but fail semantic validation?

Yes. A date may match the expected `YYYY-MM-DD` format but represent a fully booked day. A product ID may match the identifier pattern but point to no product.

### Why does TypeScript not validate `req.body`?

TypeScript checks code during development. The client sends runtime data after the code is running. A type assertion changes what the compiler believes, but it does not inspect the actual request.

### Why is `if (!value)` not always a correct required-field check?

Because valid values such as `0` and `false` are falsy. Required-field logic must distinguish a missing value from a present value that happens to be falsy.

## What I Learned

Validation is the act of converting an external claim into an internal guarantee.

The three-level model gives me a repeatable way to reason:

```text
Syntactic → Does it look right?
Type      → Is it represented correctly?
Semantic  → Does it make sense in this operation?
```
