# Backend from First Principles — Day 6 (Part 5)

# Type Validation: Is the Runtime Value Correct?

> *“A static type describes what developers intend. Runtime validation proves what the client actually sent.”*

---

## Introduction

JavaScript makes it easy to put almost any value inside a variable.

```js
let age = 24;
age = "twenty-four";
age = false;
age = [24];
```

The language allows every assignment. That flexibility is useful, but it means a backend must be careful when values come from the network.

If my service expects a number and receives an array, the program may fail far away from the controller where the bad value entered.

Type validation catches that problem at the entrance.

Type validation ensures that each incoming value uses the representation required by the API contract.

```text
name       → string
age        → integer
isActive   → boolean
hobbies    → array of strings
address    → object
```

This is especially important in JavaScript because values can be coerced in surprising ways, and in TypeScript because network data remains unknown at runtime.

## What Is a Data Type?

A data type is the kind of value a program is handling.

Think of labeled containers in a kitchen:

```text
Flour container
Water bottle
Egg carton
```

Each container is designed for a particular kind of thing. Pouring water into the flour container may technically fit, but everything that uses the container afterward will behave incorrectly.

Programming types work similarly:

```text
String  → text such as "Belema"
Number  → numeric values such as 24 or 9.5
Boolean → true or false
Array   → an ordered list of values
Object  → named properties and values
Null    → an intentional absence of a value
```

When an API says `age` is a number, that is part of its contract. The string `"24"` contains numeric characters, but it is still text.

## Why the Difference Matters

Imagine calculating a total:

```js
const total = price + deliveryFee;
```

With numbers:

```js
20 + 5; // 25
```

With strings:

```js
"20" + "5"; // "205"
```

The program does not understand that the developer meant money. It follows the rules of the values it actually received.

That is why checking types early prevents confusing errors later.

## The Basic Checks

| Expected value | Useful runtime check |
| --- | --- |
| String | `typeof value === "string"` |
| Finite number | `typeof value === "number" && Number.isFinite(value)` |
| Integer | `Number.isInteger(value)` |
| Boolean | `typeof value === "boolean"` |
| Array | `Array.isArray(value)` |
| Plain object | Object, non-null, and not an array |

The last two matter because JavaScript has historical quirks:

```js
typeof []   // "object"
typeof null // "object"
```

Therefore this check is incomplete:

```js
typeof value === "object"
```

A safer plain-object check starts like this:

```js
function isPlainObject(value) {
  return (
    typeof value === "object" &&
    value !== null &&
    !Array.isArray(value)
  );
}
```

## Numbers Need More Than `typeof`

JavaScript says `NaN` and `Infinity` are numbers:

```js
typeof NaN      // "number"
typeof Infinity // "number"
```

Most APIs do not want either. A quantity usually needs all of these rules:

```js
function isValidQuantity(value) {
  return (
    typeof value === "number" &&
    Number.isFinite(value) &&
    Number.isInteger(value) &&
    value >= 1 &&
    value <= 100
  );
}
```

Type and range rules often sit next to each other, even though the range begins to express value semantics.

## Strict Types vs Coercion

Suppose a JSON body contains:

```json
{ "age": "30", "isActive": "false" }
```

The strings resemble the intended values, but they are not a number and boolean.

A strict body contract rejects them:

```text
age must be a JSON number
isActive must be a JSON boolean
```

That is usually easier to reason about than broad coercion. JavaScript makes this particularly dangerous:

```js
Boolean("false") // true
```

If an API chooses coercion, it should parse an exact allowlist:

```js
function parseBoolean(value) {
  if (value === "true") return true;
  if (value === "false") return false;
  return undefined;
}
```

Query and path parameters naturally arrive as text, so deliberate parsing is normal there. JSON already supports native numbers and booleans, so strictness is often preferable.

### What Is Coercion?

Coercion means converting a value from one type to another.

Sometimes the developer performs it explicitly:

```js
Number("24"); // 24
```

Sometimes JavaScript performs it automatically:

```js
"5" * 2; // 10
```

Automatic coercion can make incorrect input appear to work until one unusual value arrives. Backend code is easier to understand when conversion is intentional.

This is also why I should not transform every value simply because I can. If a JSON API promises that `age` is a number, accepting both `24` and `"24"` makes the contract less clear. For query parameters, text-to-number parsing is natural because URLs carry text.

## Arrays Need Item Validation

Confirming that a value is an array is only the beginning:

```json
{ "tags": ["api", 42, null] }
```

The container has the right type, but its elements do not. The complete rule might be:

```text
tags is an array
tags contains at most 10 values
every value is a string
every string is 1–30 characters after trimming
duplicate tags are not allowed
```

Nested arrays and objects require validation all the way down. A valid outer object does not make its children valid.

## Optional, Nullable, and Missing

These contracts are not equivalent:

```ts
nickname?: string;
nickname: string | null;
nickname?: string | null;
```

- **Optional** means the property may be absent.
- **Nullable** means the property may be present with `null`.
- An empty string is still a string and needs a separate rule.

Clear nullability is important for update endpoints. In a patch request, missing may mean “leave unchanged,” while `null` may mean “clear this value.”

## TypeScript Does Not Validate HTTP

This controller is unsafe despite looking typed:

```ts
type CreateUserBody = {
  name: string;
  age: number;
};

const body = req.body as CreateUserBody;
```

The `as` keyword tells the compiler to trust the developer. It emits no runtime check. A caller can still send:

```json
{ "name": 0, "age": "old" }
```

The honest boundary type is `unknown`. A schema parser validates it and returns a typed result only on success:

```ts
const input = createUserSchema.parse(req.body);
// input is now validated and typed
```

### Compiler Time vs Runtime

This distinction took me a while to understand.

TypeScript works while developers write and build the application:

```text
Developer writes code → TypeScript checks code → JavaScript is produced
```

The HTTP request arrives later, while the program is running:

```text
Client sends JSON → Running server receives value
```

TypeScript is no longer standing at the network boundary. Runtime validation must inspect the actual value.

Writing `as CreateUserBody` is like attaching a label that says “safe” to a closed box. A schema actually opens the box and checks what is inside.

## A Manual Type Validator

```js
function validateTypes(data) {
  const errors = [];

  if (typeof data.name !== "string") {
    errors.push({ field: "name", code: "expected_string" });
  }

  if (!Number.isInteger(data.age)) {
    errors.push({ field: "age", code: "expected_integer" });
  }

  if (typeof data.isActive !== "boolean") {
    errors.push({ field: "isActive", code: "expected_boolean" });
  }

  if (!Array.isArray(data.hobbies)) {
    errors.push({ field: "hobbies", code: "expected_array" });
  } else if (!data.hobbies.every((item) => typeof item === "string")) {
    errors.push({ field: "hobbies", code: "expected_string_items" });
  }

  return errors;
}
```

## Following One Value Through the Type Check

Suppose the request contains:

```json
{ "age": "24" }
```

The process is:

```text
Raw value arrives
→ typeof value is "string"
→ contract expects an integer
→ strict JSON body rejects it
→ client receives a field-level error
```

For a query string such as `?age=24`, the contract may intentionally do this:

```text
Raw text "24"
→ confirm the complete text represents an integer
→ transform it into number 24
→ check the accepted range
→ continue with number 24
```

Same visible characters. Different input source. Different documented policy.

## Checkpoint Questions

### What is type validation?

It confirms that a runtime value has the representation the API expects, such as a string, integer, boolean, array, or non-null object.

### Why is `typeof value === "object"` not enough for an object field?

Because arrays and `null` also report `"object"` in JavaScript. The validator must exclude them when it expects a normal object.

### Why is `typeof value === "number"` not always enough?

Because `NaN` and `Infinity` are also numbers in JavaScript. Many contracts require a finite number, a safe integer, and an accepted range.

### What is the danger of `Boolean("false")`?

It produces `true` because every non-empty string is truthy. Boolean text should be parsed through exact accepted values.

## What I Learned

Type validation is the bridge between untyped external data and dependable application code.

The rules I want to remember are:

```text
Treat runtime input as unknown.
Avoid accidental coercion.
Check arrays and objects precisely.
Validate nested values.
Define optionality and nullability explicitly.
```

Correct types make data usable. They do not yet make it meaningful. Part 6 covers semantic validation and business rules.
