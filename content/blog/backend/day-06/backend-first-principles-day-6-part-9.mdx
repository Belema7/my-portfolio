# Backend from First Principles — Day 6 (Part 9)

# Frontend vs Server-Side Validation

> *“Frontend validation helps the user. Server-side validation protects the system. A good product uses both, but it never confuses their authority.”*

---

## Introduction

The same email field may be checked in a browser and again in an API. That is not necessarily wasteful duplication. The two checks run in different trust environments and serve different purposes.

| Aspect | Frontend validation | Server-side validation |
| --- | --- | --- |
| Primary purpose | Fast, helpful user experience | Security and data integrity |
| Runs | Before or while sending a request | At the authoritative API boundary |
| Can be bypassed | Yes | Not if every write path enforces it |
| Has trusted database state | Usually no | Yes |
| Final authority | No | Yes |

## Frontend Validation Is Excellent UX

A browser can respond immediately:

- mark a missing field;
- show a password requirement checklist;
- display a character counter;
- catch mismatched confirmation values;
- move focus to the first invalid field;
- preserve form state while the user fixes an error.

Without client-side validation, every small mistake requires a network round trip. On slow or unreliable connections, that creates a frustrating experience.

Accessible frontend validation should also connect messages to fields, avoid relying only on color, announce errors to assistive technology, and preserve what the user entered when possible.

## Why the Frontend Cannot Enforce Security

The client runs on a device the user controls. A caller can bypass browser code by:

- sending requests with `curl`, Postman, or a script;
- changing JavaScript in developer tools;
- disabling JavaScript;
- intercepting and modifying a request;
- calling an endpoint from an old application version;
- building an entirely different client.

This request never needs to touch the official form:

```bash
curl -X POST https://api.example.com/users \
  -H 'Content-Type: application/json' \
  -d '{"email":"bad","role":"admin"}'
```

If the backend trusts the frontend, the API has no defense.

## The Server Owns the Contract

The server must independently enforce:

```text
required fields
types and formats
length and size limits
authorization
uniqueness and existence
state transitions
database constraints
```

The server’s answer is authoritative because it controls the protected operation and current state.

Frontend and backend can disagree temporarily. Another user might claim a username after the browser checks availability but before the form is submitted. The backend must decide the final result and the frontend must display it gracefully.

## A Complete Form Flow

```text
User types an email
    ↓
Frontend checks required/format rules
    ↓
Frontend sends request
    ↓
Backend validates the whole request again
    ↓
Backend checks current uniqueness and policy
    ↓
Database constraint protects against races
    ↓
Frontend renders success or field-level error
```

Each layer adds something the previous layer cannot guarantee.

## Sharing Schemas Without Sharing Trust

In a TypeScript monorepo, frontend and backend may share a schema or generated contract. This can reduce drift:

```ts
export const registrationSchema = z.object({
  name: z.string().trim().min(1).max(80),
  email: z.string().trim().email(),
});
```

The browser can use it for feedback and the server can use it for enforcement.

But shared code does not make frontend results trusted. The server still executes the schema on the received payload. It should also own rules that require secrets, permissions, or current database state.

For systems with separate stacks, OpenAPI or JSON Schema can help generate client types and document constraints. Contract tests can detect drift.

## Do Not Expose Every Internal Rule

Frontend messages should be helpful, but some server rules are security-sensitive. Login and password reset flows should avoid revealing whether an account exists. Fraud rules should not explain how to evade them. Authorization failures should not expose private resource details.

The user-facing response is a product and security decision, not a direct dump of internal validation state.

## Keep Rules Consistent

The frustrating failure mode is a form that promises one rule while the server enforces another:

```text
Frontend: password requires 8 characters
Backend: password requires 12 characters
```

Ways to reduce drift include:

- shared schemas where architecture permits;
- a machine-readable API contract;
- generated client types;
- integration tests for boundary values;
- stable server error codes;
- one documented source of truth.

The server remains authoritative even when rules are shared.

## What I Learned

The golden rule is:

> **Frontend validation is for usability. Server validation is non-negotiable for correctness and security.**

The best experience does not choose one or the other. It uses immediate client feedback and authoritative server enforcement as complementary layers.
