# Backend from First Principles — Day 4 (Part 9)

# Content Negotiation: Agreeing on the Format

> *"Serialization is not only about converting objects into JSON. It is also about agreement. The client and server need to know what format is being sent, what format is wanted back, and what to do when they cannot agree."*

---

## Introduction

So far, I have mostly talked about JSON as if every API always uses JSON.

For many modern web APIs, that is a fair default.

But HTTP is more flexible than that.

An API can theoretically support multiple response formats:

```text
JSON
XML
CSV
YAML
Plain text
Binary formats
```

That raises an important question:

> **How does the client tell the server what it is sending and what it wants back?**

The answer is HTTP headers.

The two most important ones for this topic are:

```http
Content-Type
Accept
```

They look similar at first, but they answer different questions.

---

## Topic 9.1 — What Content Negotiation Means

Content negotiation is the process where a client and server agree on the representation of a resource.

In simpler words:

```text
Client: "Here is the format I am sending."
Client: "Here is the format I want back."
Server: "Here is the format I chose for the response."
```

The same logical resource can have different representations.

For example, a user can be represented as JSON:

```json
{
  "id": 15,
  "name": "Belema"
}
```

Or XML:

```xml
<user>
  <id>15</id>
  <name>Belema</name>
</user>
```

The user is the same concept.

The serialization format is different.

Content negotiation is how HTTP makes that choice explicit.

---

## Topic 9.2 — Content-Type vs Accept

These two headers are easy to confuse.

| Header | Where it appears | Meaning |
| --- | --- | --- |
| `Content-Type` | Request or response | What format this body is in |
| `Accept` | Request | What format the client wants back |

### Content-Type

`Content-Type` describes the body being sent.

Request example:

```http
POST /users HTTP/1.1
Content-Type: application/json

{
  "name": "Belema"
}
```

This means:

```text
The request body is JSON.
```

Response example:

```http
HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 15,
  "name": "Belema"
}
```

This means:

```text
The response body is JSON.
```

### Accept

`Accept` describes what the client would like to receive.

```http
GET /users/15 HTTP/1.1
Accept: application/json
```

This means:

```text
Please send the response as JSON if you can.
```

The clean mental model is:

```text
Content-Type = what I am sending
Accept = what I want back
```

---

## Topic 9.3 — JSON as the Default API Format

Most APIs I build as a web developer will probably use JSON by default.

For example:

```http
POST /api/users HTTP/1.1
Content-Type: application/json
Accept: application/json
```

This says:

```text
I am sending JSON.
I want JSON back.
```

That is the normal REST API flow.

The backend can then:

1. Read `Content-Type`
2. Choose the right parser
3. Deserialize the body
4. Validate the data
5. Process the request
6. Serialize the response
7. Send `Content-Type` on the response

The headers guide the serialization pipeline.

---

## Topic 9.4 — Express Example

In Express, `req.accepts()` can help check what response format the client accepts.

```js
app.get("/users/:id", (req, res) => {
  const user = {
    id: Number(req.params.id),
    name: "Belema",
  };

  if (req.accepts("json")) {
    return res.json(user);
  }

  if (req.accepts("xml")) {
    return res
      .type("application/xml")
      .send(`<user><id>${user.id}</id><name>${user.name}</name></user>`);
  }

  return res.status(406).json({
    error: "Not Acceptable",
  });
});
```

In a real application, I would use a proper XML serializer instead of manually building XML strings.

But the idea is the important part:

```text
Check what the client accepts.
Serialize into a supported format.
Set the response Content-Type.
```

## Topic 9.5 — 406 Not Acceptable

What happens if a client asks for a format the server cannot provide?

Example:

```http
GET /users/15 HTTP/1.1
Accept: application/xml
```

If the server only supports JSON, it may respond:

```http
HTTP/1.1 406 Not Acceptable
Content-Type: application/json

{
  "error": "Not Acceptable"
}
```

`406 Not Acceptable` means:

```text
The server understood the request, but cannot produce a response in a format acceptable to the client.
```

In practice, many APIs are simpler and always return JSON. But knowing `406` helps me understand the HTTP model more deeply.

---

## Topic 9.6 — 415 Unsupported Media Type

There is another status code that belongs near this topic: `415 Unsupported Media Type`.

`406` is about the response format.

`415` is about the request body format.

Example:

```http
POST /users HTTP/1.1
Content-Type: application/xml

<user>
  <name>Belema</name>
</user>
```

If the server only accepts JSON request bodies, it can reject this with:

```http
HTTP/1.1 415 Unsupported Media Type
Content-Type: application/json

{
  "error": "Unsupported Media Type"
}
```

The distinction is useful:

| Status | Problem |
| --- | --- |
| `406 Not Acceptable` | Server cannot send a response in the requested format |
| `415 Unsupported Media Type` | Server cannot process the request body format |

This connects HTTP status codes directly to serialization decisions.

## My Biggest Realization

Before this, I thought `Content-Type: application/json` was just a header I copied into requests.

Now I see it as part of the API contract.

It tells the other side how to interpret the body.

`Accept` completes the conversation by saying what the client wants back.

Together, they make serialization explicit instead of magical.

```text
Data format is not a guess.
It is part of the HTTP conversation.
```

## Part 9 Complete!

## Final Summary

**1. Content negotiation is about agreeing on representation**

The same resource can be represented as JSON, XML, or another format.

**2. `Content-Type` describes the body being sent**

It appears on requests and responses.

**3. `Accept` describes what the client wants back**

The server can use it to choose a response format.

**4. `406 Not Acceptable` is for unsupported response formats**

The server cannot produce a representation the client accepts.

**5. `415 Unsupported Media Type` is for unsupported request body formats**

The server cannot parse or process the format the client sent.

### Checkpoint Questions

**What does `Content-Type` mean?**

It tells the receiver what format the current body uses.

**What does `Accept` mean?**

It tells the server what response formats the client can accept.

**When would a server return `406 Not Acceptable`?**

When it cannot produce a response in any format the client accepts.

**When would a server return `415 Unsupported Media Type`?**

When the request body uses a format the server does not support.
