# Backend from First Principles — Day 4 (Part 1)

# The Language Barrier: Why Serialization Exists

> *"Until now, I understood how a request reaches the correct backend route. But I had skipped an important question: how does the data inside that request move from a JavaScript application into a completely separate program? Today I learned that objects do not travel through the network. Their data must first be translated into a shared representation."*

---

## Introduction

During Day 3, I learned how a server matches an HTTP method and URL to the correct controller.

For example:

```http
POST /users
Content-Type: application/json
```

I understood the route. I understood the HTTP method. I even understood what the controller should do.

But then I asked a more basic question:

> **How does the JavaScript object from my frontend actually arrive at the backend?**

At first, I imagined the browser sending the object itself across the internet. That sounds reasonable, but it is not what happens.

The object exists only inside the browser's memory. A backend running on another computer cannot reach into that memory and take it.

That is the language barrier serialization solves.

---

## Topic 1.1 — Two Programs, Two Separate Worlds

Imagine a registration form creates this JavaScript object:

```ts
const newUser = {
  name: "Belema",
  email: "belema@example.com",
  age: 22,
};
```

JavaScript understands this value because it created it and stores it in the browser's memory.

The backend may also work with an object that looks almost identical:

```ts
const user = {
  name: "Belema",
  email: "belema@example.com",
  age: 22,
};
```

But these are not the same object. They live in different processes, possibly on different operating systems, in different countries.

Even if both applications use TypeScript, they still do not share memory.

```text
Browser memory                  Server memory

JavaScript object     ✕        Backend object
```

The similarity of the code can hide the physical separation between the two programs.

### A Remote Office Analogy

Imagine two offices in different countries. Each office has its own filing cabinets. An employee in Office A cannot place a folder directly inside a cabinet in Office B.

Office A must copy the important information into an agreed document format, send it, and allow Office B to create a new folder from that information.

The original folder never travels. Only a representation of its information does.

That is exactly what happens with application objects.

---

## Topic 1.2 — What the Network Actually Transports

A network does not understand JavaScript objects, Python dictionaries, Java classes, NestJS DTOs, or TypeScript interfaces.

At the lowest useful level, networks transport bytes.

```text
Application data → Bytes → Network → Bytes → Application data
```

Before structured information can travel, the sender must convert it into a representation with clear rules. The receiver must know those same rules so it can interpret the incoming data correctly.

For web APIs, that shared representation is commonly JSON.

### TypeScript Types Do Not Travel

Suppose the frontend defines this interface:

```ts
interface CreateUserRequest {
  name: string;
  email: string;
  age: number;
}
```

This interface helps during development, but TypeScript removes it when the code becomes JavaScript. It does not become part of the HTTP request.

The backend receives values, not frontend type guarantees.

That gave me an important realization:

> **Frontend types improve development, but backend validation protects the system.**

A user can bypass the frontend completely and send any request they want.

---

## Topic 1.3 — JSON as a Shared Language

JSON stands for **JavaScript Object Notation**, but it is not a JavaScript object and it is not limited to JavaScript.

It is a text-based format understood by almost every major programming language.

The frontend object:

```ts
const user = {
  name: "Belema",
  age: 22,
  isActive: true,
};
```

can be represented as JSON text:

```json
{
  "name": "Belema",
  "age": 22,
  "isActive": true
}
```

The information is similar, but the representation is different.

### The Translator Analogy

Imagine one person speaks Amharic and another speaks French. Instead of learning each other's language, they agree to communicate through English.

English becomes their shared language.

In the same way, the frontend does not need to understand the backend's internal programming language. Both applications only need to understand the agreed data format.

```text
Frontend object → JSON → Backend object
```

JSON is the common language in the middle.

### Content-Type Identifies the Format

When the frontend sends JSON, the request normally includes:

```http
Content-Type: application/json
```

This header tells the backend how the request body is formatted. Without that information, the receiver may not know which parser to use.

It is like writing “English” on the outside of a document before sending it to a multilingual office.

---

## Topic 1.4 — Not Every JavaScript Value Fits Inside JSON

JSON supports a deliberately small set of values:

| JSON value | Example |
| --- | --- |
| String | `"Belema"` |
| Number | `22` |
| Boolean | `true` |
| Null | `null` |
| Array | `["admin", "writer"]` |
| Object | `{ "name": "Belema" }` |

JavaScript supports additional values that JSON cannot represent directly.

### Functions Describe Behavior

```ts
const user = {
  name: "Belema",
  greet() {
    return `Hello, ${this.name}`;
  },
};
```

The backend needs the user's data, not the function living in browser memory. Functions are therefore not normal JSON data.

### Dates Become Strings

A JavaScript `Date` can become an ISO string:

```json
{
  "createdAt": "2026-07-18T10:00:00.000Z"
}
```

The receiver gets a string. It must decide whether and how to convert that string into its own date type.

### Other Important Limitations

* Properties containing `undefined` may disappear.
* `BigInt` is not supported directly.
* `Map` and `Set` need an intentional conversion.
* Symbols and class methods are not preserved.
* Circular object references cannot be represented by standard JSON.

JSON transfers structured data, not the complete behavior and identity of a JavaScript object.

---

## Topic 1.5 — The Name of the Translation Process

The conversion into a transferable representation is called **serialization**.

```ts
const requestBody = JSON.stringify(newUser);
```

The reverse operation is called **deserialization**.

```ts
const receivedUser = JSON.parse(requestBody);
```

The complete idea looks like this:

```text
Object
  ↓
Serialization
  ↓
JSON text
  ↓
Network transmission
  ↓
Deserialization
  ↓
New object
```

The receiver creates a new value from the representation. The original in-memory object does not physically cross the network.

## Part 1 Complete!

## Final Summary

**1. Frontend and backend applications do not share memory**

Each program owns its own objects and data structures.

**2. Networks transport bytes, not programming-language objects**

Application data needs an agreed representation before it can travel.

**3. JSON provides a shared language**

Different platforms and programming languages can produce and understand it.

**4. TypeScript types do not protect the backend**

They disappear at runtime, so incoming data must still be validated.

**5. Serialization preserves data, not object identity or behavior**

Functions, prototypes, dates, maps, sets, and other special values need careful handling.

### Checkpoint Questions

**Why can't a frontend send its JavaScript object directly to a backend?**

Because the object exists only in the browser's memory. The backend runs in a separate process and needs a transferable representation of the data.

**What role does JSON play?**

JSON provides an agreed, language-independent text format that both sender and receiver understand.

**Do TypeScript interfaces travel with an HTTP request?**

No. They are development-time checks and are removed before the JavaScript runs.

**Does deserialization recreate the original object?**

It creates a new in-memory value containing data reconstructed from the serialized representation.
