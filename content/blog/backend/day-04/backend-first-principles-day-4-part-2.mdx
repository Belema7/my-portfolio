# Backend from First Principles — Day 4 (Part 2)

# Following Data Through a Complete Request and Response

> *"In Part 1, I learned that objects do not cross the network. Applications serialize their data into a shared representation and reconstruct new values on the other side. Today I want to stop looking at serialization as an isolated definition and follow it through a real request from beginning to end."*

---

## Introduction

Learning the definitions of serialization and deserialization was useful:

```text
Serialization   → Data becomes transferable
Deserialization → Transferable data becomes usable again
```

But I still wanted to know where these operations happen during a real application request.

Does the frontend serialize the data manually? Does the backend call `JSON.parse()` inside every controller? When does validation happen? When is the response serialized?

To answer those questions, I followed one scenario through the whole system.

---

## The Scenario — Updating a User Profile

Imagine a logged-in user changes their display name and biography.

The frontend needs to send:

```http
PATCH /api/profile
```

The backend must validate the input, update the database, and return the updated profile.

What looks like one simple button click actually crosses several boundaries:

```text
Form → Frontend object → HTTP request → Backend value
     → Database → Backend response → Frontend value → UI
```

Let's follow it one step at a time.

---

## Topic 2.1 — The Request Begins in Browser Memory

### Step 1 — The User Submits the Form

The frontend collects the form values:

```ts
const formData = {
  displayName: "Belema Girma",
  bio: "Frontend developer learning backend from first principles.",
};
```

At this moment, `formData` is an ordinary JavaScript object in browser memory. Nothing has crossed the network.

### Step 2 — Frontend Validation Improves the Experience

The frontend may check whether the display name is empty or the biography is too long.

```ts
if (!formData.displayName.trim()) {
  showError("Display name is required");
}
```

This gives the user quick feedback, but it is not a security boundary. Someone can skip the form and send a request directly with another tool.

> **Frontend validation helps the user. Backend validation protects the application.**

### Step 3 — The Data Is Serialized

Before the request body can be transmitted, the object becomes JSON text:

```ts
const body = JSON.stringify(formData);
```

Conceptually, the result looks like this:

```json
{
  "displayName": "Belema Girma",
  "bio": "Frontend developer learning backend from first principles."
}
```

This is the first serialization point.

---

## Topic 2.2 — Building and Sending the HTTP Request

### Step 4 — The Frontend Creates the Request

The frontend sends the serialized body with instructions for the backend:

```ts
await fetch("/api/profile", {
  method: "PATCH",
  headers: {
    "Content-Type": "application/json",
  },
  body: JSON.stringify(formData),
});
```

The request contains different kinds of information:

| Request part | Purpose |
| --- | --- |
| Method | Describes the operation |
| Path | Identifies the resource |
| Headers | Provide metadata and instructions |
| Body | Carries the serialized profile data |

### Step 5 — Text Becomes Bytes

Serialization and encoding are related, but they are not the same operation.

Serialization creates a structured representation such as JSON text. Text encoding converts that text into bytes, commonly using UTF-8.

```text
JavaScript object
      ↓ serialization
JSON text
      ↓ UTF-8 encoding
Bytes
      ↓ network
```

HTTPS then protects those bytes during transmission. Encryption does not replace serialization; it protects the serialized data while it travels.

This distinction was important for me because I previously treated serialization, encoding, and encryption as if they meant the same thing.

---

## Topic 2.3 — The Request Enters the Backend

### Step 6 — Infrastructure Receives the Request

The request may pass through a firewall, load balancer, or reverse proxy before reaching the backend application.

The server reads the HTTP message and identifies:

```text
Method: PATCH
Path: /api/profile
Content-Type: application/json
Body: JSON data
```

### Step 7 — Routing Finds the Correct Handler

This connects directly to Day 3.

The router matches the method and path:

```text
PATCH + /api/profile → Profile controller
```

Routing decides which code should handle the request. It does not make the incoming data trustworthy.

### Step 8 — The Body Is Deserialized

The backend converts the JSON request body into a value the application can use.

In a low-level example, this might involve:

```ts
const data = JSON.parse(rawBody);
```

Frameworks usually do this automatically. Express commonly uses JSON middleware, and NestJS builds on that request-processing pipeline.

By the time the controller reads the body, deserialization may already be complete.

That explains why I rarely write `JSON.parse()` inside a controller even though deserialization still happens.

---

## Topic 2.4 — Deserialized Does Not Mean Trusted

### Step 9 — Authentication and Authorization

Before updating the profile, the backend needs to know:

1. Who is making this request?
2. Is that user allowed to update this profile?

Authentication establishes identity. Authorization checks permission.

Successfully parsing JSON answers neither question.

### Step 10 — Transformation and Validation

Consider this valid JSON:

```json
{
  "displayName": "",
  "bio": 9000,
  "isAdmin": true
}
```

The syntax is valid, so it can be deserialized. But the application data is invalid and potentially dangerous.

The backend may need to:

* Require a non-empty display name.
* Ensure the biography is a string.
* Enforce a maximum length.
* Reject or remove unknown fields such as `isAdmin`.
* Apply business-specific rules.

| Process | Question it answers |
| --- | --- |
| Deserialization | Can I reconstruct a program value? |
| Transformation | Should any values change type or shape? |
| Validation | Does this value follow the rules? |
| Authorization | May this user perform the operation? |

This was one of my biggest lessons:

> **Valid JSON is not the same as valid application data.**

---

## Topic 2.5 — Business Logic and the Database

### Step 11 — The Controller Coordinates the Request

After the request passes the necessary checks, the controller calls the appropriate service.

The service applies business rules and asks the database to update the profile.

```text
Controller → Profile service → Database
```

The database returns a record to the backend. That record is now an in-memory value inside the server application.

It still cannot be sent directly to the browser.

---

## Topic 2.6 — The Response Makes the Return Journey

### Step 12 — The Backend Creates a Response Value

The backend prepares a safe response:

```ts
const response = {
  id: 15,
  displayName: "Belema Girma",
  bio: "Frontend developer learning backend from first principles.",
};
```

Sensitive internal fields should not be included simply because they exist in the database record.

### Step 13 — The Response Is Serialized

The backend converts the response value into JSON. Frameworks commonly perform this automatically when a controller returns an object.

This is the second serialization point in the full cycle.

```text
Backend object → JSON response → Network
```

### Step 14 — The Frontend Deserializes the Response

The browser receives the response and reconstructs a JavaScript value:

```ts
const updatedProfile = await response.json();
```

Despite its convenient name, `response.json()` does not return raw JSON text. It reads the response body and parses it into a JavaScript value.

### Step 15 — The UI Updates

The frontend uses the new object to update the screen.

```text
JSON response → JavaScript object → Updated profile UI
```

The round trip is complete.

---

## The Complete Lifecycle

```text
User submits form
      ↓
Frontend creates object
      ↓
Frontend validates for usability
      ↓
Object is serialized into JSON
      ↓
JSON is encoded, encrypted, and transmitted
      ↓
Backend parses HTTP and matches the route
      ↓
Request body is deserialized
      ↓
Backend authenticates, authorizes, transforms, and validates
      ↓
Business logic updates the database
      ↓
Backend creates and serializes a response
      ↓
Frontend deserializes the response
      ↓
UI updates
```

What looked like “send an object to the backend” is actually a carefully coordinated sequence of conversions and checks.

## Part 2 Complete!

## Final Summary

**1. Serialization happens in both directions**

The frontend serializes the request, and the backend serializes the response.

**2. Deserialization also happens in both directions**

The backend deserializes the request, and the frontend deserializes the response.

**3. Framework automation does not remove the process**

Express, NestJS, and browser APIs often hide the low-level work, but serialization still happens.

**4. Parsing, validation, and authorization solve different problems**

A request can contain valid JSON while still being invalid, unsafe, or forbidden.

**5. The original object never crosses the network**

Each side constructs new in-memory values from the transferred representation.

### Checkpoint Questions

**How many serialization points are in a normal request-response cycle?**

Usually two: the client serializes the request, and the server serializes the response.

**Why don't controllers normally call `JSON.parse()` manually?**

Backend frameworks or middleware commonly deserialize JSON bodies before controller code runs.

**Is successfully parsed JSON safe to use immediately?**

No. It must still pass validation, authorization, and any required business rules.

**What does `response.json()` return?**

It reads and parses the JSON response body, returning a JavaScript value.
