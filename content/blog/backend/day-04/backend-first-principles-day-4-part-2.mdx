# Backend from First Principles — Day 4 (Part 2)

# Serialization vs Deserialization & The Request Lifecycle

> *"Serialization and deserialization are two opposite processes used whenever data moves between systems. They are essential in frontend-backend communication, REST APIs, mobile applications, microservices, message queues, caching, file storage, databases, and distributed systems. Today's lesson explores these concepts in detail and walks through the complete request and response lifecycle."*

---

## What Is Serialization?

Serialization is the process of converting an in-memory value into a standardized representation that can be transmitted or stored.

For example, a JavaScript application may have this object:

```ts
const user = {
  id: 1,
  name: "Belema",
  isActive: true,
};
```

This object exists only inside the application's memory. To send it through an HTTP request, it can be serialized into JSON:

```ts
const json = JSON.stringify(user);
```

The original object is now represented as text that can be sent through a network, stored in a file, placed in browser storage, saved in a cache, or published to a message queue.

---

## What Is Deserialization?

Deserialization is the reverse process. It converts serialized data back into a usable in-memory value.

Suppose an application receives this JSON string:

```ts
const json = '{"id":1,"name":"Belema","isActive":true}';
```

It can deserialize the string using:

```ts
const user = JSON.parse(json);
```

The result is a JavaScript object that the application can access normally.

---

## The Two Processes Are Opposites

Serialization and deserialization are reverse operations:

```text
Program object → Serialization → Serialized representation → Deserialization → New program object
```

The data completes a round trip, but the final object is not the exact same object in memory. The two objects may contain equivalent data, but they are separate values. Serialization does not physically move an object from one program into another; it creates a representation of the object's data.

### A Blueprint Analogy

Imagine sending a table to someone in another country. You cannot send the physical table through email. Instead, you create a blueprint. Creating the blueprint is similar to serialization. The receiver reads the blueprint and builds a new table. That reconstruction is similar to deserialization. The receiver gets a new table created from the shared representation.

---

## Serialization and Deserialization in Both Directions

A complete request-response cycle uses both operations twice:

**Request direction:**
Frontend object → Frontend serialization → JSON request → Backend deserialization → Backend object

**Response direction:**
Backend object → Backend serialization → JSON response → Frontend deserialization → Frontend object

---

## JSON Parsing and Stringifying

### JSON.stringify()

`JSON.stringify()` converts a JavaScript value into JSON text. A useful mental model is: Object → String.

### JSON.parse()

`JSON.parse()` converts valid JSON text into a JavaScript value. A useful mental model is: String → Object. 

Parsing can produce more than objects; it can return arrays, strings, numbers, booleans, or `null`.

---

## What Serialization Does Not Preserve

JSON supports a limited set of values. JavaScript supports many additional values that may be removed, changed, or cause errors during serialization.

* **Functions are not serialized**: The function is removed.
* **undefined is not a JSON value**: Properties set to `undefined` are omitted.
* **Dates become strings**: Serialization preserves the date representation as a string, not the original JavaScript `Date` instance.
* **Class instances become plain objects**: Class identity, prototypes, and methods are not preserved.
* **Map and Set need conversion**: They serialize to empty objects unless converted to arrays first.
* **BigInt is not supported directly**: It usually throws an error unless converted to a string.
* **Circular references cause errors**: Standard JSON cannot represent circular references and will throw an error.

---

## Crucial Distinctions

### Deserialization Is Not Validation

Valid JSON can still contain invalid application data. Deserialization asks: *Can this serialized representation be converted into a program value?* Validation asks: *Does the resulting value satisfy the application's required rules?*

Parsed data is still untrusted.

### Deserialization Is Not Transformation

Deserialization reconstructs a value. Transformation changes that value into another type (e.g., converting a string age "22" to a number 22).

### Serialization Is Not Encoding, Encryption, or Compression

* **Encoding** converts text into network bytes.
* **Encryption** protects data confidentiality (e.g., HTTPS).
* **Compression** reduces the size of the data.

Serialization simply prepares data for transport or storage.

---

## The Complete Request & Response Lifecycle

Serialization and deserialization do not happen in isolation. They are part of a larger lifecycle. Suppose a user updates their profile.

### The Frontend Creates an In-Memory Value
The frontend collects form values and constructs a JavaScript object. This object exists only in browser memory.

### Frontend Validation
The frontend may validate the input (e.g., ensuring the name is not empty). Frontend validation improves usability but is not a security boundary.

### Request Serialization
The frontend converts the JavaScript object into JSON text using `JSON.stringify()`. This is the first serialization point.

### The Frontend Constructs the HTTP Request
The frontend sends the request with the serialized JSON body, specifying headers like `Content-Type: application/json`. 

### Text Encoding and Network Transmission
The JSON text is encoded into bytes and sent over the network, traversing routers, ISPs, and cloud infrastructure. DNS resolves the domain name, and HTTPS encrypts the traffic.

### Infrastructure and HTTP Parsing
The request reaches load balancers and reverse proxies before hitting the backend. The backend server decodes the bytes and parses the raw HTTP request, identifying the method, path, and headers.

### Route Matching and Middleware
The router finds the matching endpoint (e.g., `PATCH /profile`). The request passes through middleware (logging, CORS, rate limiting).

### Request Deserialization
The backend reads the JSON text body and deserializes it into a usable backend value using `JSON.parse()` (often handled automatically by framework middleware like `express.json()`).

### Authentication and Authorization
The backend verifies the user's identity (Authentication) and ensures they have permission to perform the action (Authorization).

### Transformation and Validation
The deserialized payload is transformed (e.g., strings to numbers) and validated against the API schema (e.g., using a NestJS DTO and ValidationPipe). Unknown fields may be stripped out.

### Controller Execution and Business Logic
The controller coordinates the request, passing data to a service where business rules are applied (e.g., checking if the profile exists).

### Database Interaction
The backend service communicates with the database to update the profile. The database query is executed, and the updated record is returned to the service.

### Response Creation
The backend creates a response object containing the updated profile or a success message. This is still an in-memory backend object.

### Response Serialization
The backend serializes the response object into JSON text. Frameworks like Express or NestJS usually handle this automatically when returning an object from a controller.

### Network Transmission (Return)
The serialized JSON response is encoded into bytes and sent back over the network to the client.

### Frontend Deserialization
The frontend receives the HTTP response and reads the JSON body. It uses `response.json()` to deserialize the text back into a usable JavaScript object.

### Frontend Usage
The frontend uses the deserialized data to update the UI, completing the full round-trip lifecycle!

---

## Final Summary

The most important rule is:
> Serialization creates a transferable representation of data. Deserialization reconstructs a new in-memory value from that representation.

The original object does not cross the network, types do not travel with it, and parsed data must still be validated before it can be trusted. Understanding this lifecycle is critical for debugging, security, and building robust APIs.
