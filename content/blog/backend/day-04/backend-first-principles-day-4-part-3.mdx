# Backend from First Principles — Day 4 (Part 3)

# JSON, XML, and YAML: Same Data, Different Jobs

> *"In the first two parts of Day 4, I learned why serialization exists and followed serialized data through a complete request and response. But that created another question: if JSON already works, why do XML and YAML still exist? Today I learned that serialization formats are not interchangeable decorations. Each one was shaped by a different problem."*

---

## Introduction

Imagine I need to represent one user:

```ts
const user = {
  name: "Belema",
  age: 22,
  isStudent: true,
};
```

My first instinct is to use JSON because that is what I usually see in APIs.

But the same information can be represented in several ways.

### JSON

```json
{
  "name": "Belema",
  "age": 22,
  "isStudent": true
}
```

### XML

```xml
<user>
  <name>Belema</name>
  <age>22</age>
  <isStudent>true</isStudent>
</user>
```

### YAML

```yaml
name: Belema
age: 22
isStudent: true
```

The syntax changes, but the underlying information remains similar.

So why do we need three formats?

> **Because different systems care about different things.**

Some prioritize simple API communication. Some need strict document structures and long-term compatibility. Others need configuration files that humans can edit comfortably.

---

## Topic 3.1 — What Is a Serialization Format?

A serialization format defines rules for representing structured information so it can be stored or transmitted.

The format answers questions such as:

* How are objects represented?
* How are lists represented?
* How are strings and numbers distinguished?
* How is nesting expressed?
* How does a parser know whether the data is valid?

### A Shipping Container Analogy

Factories produce many different products, but shipping companies need standardized ways to transport them.

A container does not care whether it holds shoes, electronics, or furniture. It provides an agreed structure that cranes, ships, ports, and trucks understand.

Serialization formats play a similar role.

```text
Application data → Agreed format → Storage or transport
```

Different containers are useful for different jobs. A refrigerated container and a normal dry container both transport goods, but they solve different problems.

That is why software has more than one serialization format.

---

## Topic 3.2 — Text-Based and Binary Formats

Serialization formats fall into two broad groups.

### Text-Based Formats

JSON, XML, and YAML can be opened and read as text. This makes them easier to inspect, debug, log, compare, and edit manually.

The trade-off is that text may include extra characters and require more space than a specialized binary representation.

### Binary Formats

Formats such as Protocol Buffers and MessagePack are designed primarily for software rather than direct human reading.

They can offer smaller messages, strict schemas, or efficient processing, but they usually require specialized tools.

| Text-based formats | Binary formats |
| --- | --- |
| Human-readable | Primarily machine-readable |
| Easy to inspect manually | Usually needs a decoder or schema |
| Common in APIs and configuration | Common in performance-sensitive systems |
| Often more verbose | Often more compact |

This article focuses on text-based formats. Binary serialization deserves its own lesson later in Day 4.

## Topic 3.3 — JSON: The Default Choice for Web APIs

JSON stands for **JavaScript Object Notation**. Although JavaScript inspired its syntax, JSON is language-independent.

JavaScript, Python, Java, C#, Go, PHP, Rust, and many other languages can all read and produce JSON.

### Why JSON Fits Web APIs

JSON became a common API format because it offers a useful balance:

* The syntax is relatively small and predictable.
* Objects and arrays map naturally to common application data.
* Browsers support it directly.
* Nearly every backend framework supports it.
* Developers can inspect it without special tools.

A REST API can identify the response format with:

```http
Content-Type: application/json
```

The frontend can then parse the response:

```ts
const user = await response.json();
```

### A Real API Example

```json
{
  "id": 15,
  "name": "Belema",
  "roles": ["user", "writer"],
  "profile": {
    "country": "Ethiopia",
    "isPublic": true
  }
}
```

This structure is easy to map into objects and arrays in most programming languages.

### JSON's Limitations

JSON is not perfect.

* It does not support comments in standard JSON.
* It has a small set of value types.
* Dates are normally represented as strings.
* It does not define a schema by itself.
* Large or highly specialized messages may benefit from other formats.

JSON is popular because it is a strong general-purpose choice, not because it solves every possible problem.

---

## Topic 3.4 — XML: Explicit Structure and Mature Standards

XML stands for **Extensible Markup Language**. It represents information using elements, attributes, and opening and closing tags.

```xml
<user id="15">
  <name>Belema</name>
  <roles>
    <role>user</role>
    <role>writer</role>
  </roles>
</user>
```

### Why XML Still Exists

When I first saw XML, I thought it was simply an older and more verbose version of JSON. That is too simplistic.

XML has a mature ecosystem for:

* Strict schemas and validation.
* Namespaces that prevent naming conflicts.
* Document-oriented data.
* Transformations and queries.
* Enterprise standards developed over many years.

This is why XML still appears in SOAP services, banking systems, government systems, publishing, document exchange, and long-lived enterprise integrations.

### The Main Trade-Off

XML is explicit, but that explicitness creates more syntax.

```xml
<name>Belema</name>
```

Both tags repeat the field name. For simple API payloads, JSON is often more concise. For complex documents and systems built around XML standards, that additional structure can be valuable.

> **Verbose does not automatically mean useless. Sometimes verbosity carries structure and guarantees.**

---

## Topic 3.5 — YAML: Configuration Designed for Humans

YAML is commonly expanded as **YAML Ain't Markup Language**. It focuses strongly on human-readable structured data.

```yaml
server:
  port: 3000
  environment: production

database:
  host: localhost
  name: portfolio
```

### Where YAML Is Common

YAML is widely used for configuration and automation, including:

* Docker Compose files.
* Kubernetes manifests.
* GitHub Actions workflows.
* CI/CD pipelines.
* Application configuration.

Instead of primarily carrying data between a browser and a server, YAML often tells software how it should run.

### Why Developers Like It

YAML removes much of the punctuation found in JSON and XML. That can make configuration easier to scan and edit.

But the clean appearance has a trade-off: indentation is meaningful.

```yaml
database:
  host: localhost
```

Changing indentation can change the structure or make the file invalid.

YAML also has more complex parsing rules than its simple appearance suggests. Applications should use trusted, safe parsers and avoid loading untrusted YAML with unsafe features enabled.

### YAML Is Usually Not the Default API Format

YAML can represent API data, but modern browser-server communication usually favors JSON because browser tooling and API conventions support it more directly.

YAML's strongest role is human-managed configuration.

---

## Topic 3.6 — Comparing the Three Formats

| Feature | JSON | XML | YAML |
| --- | --- | --- | --- |
| Primary strength | Web data exchange | Structured documents and mature standards | Human-edited configuration |
| Human readability | Good | Moderate | Very good when kept simple |
| Syntax size | Relatively compact | Usually verbose | Usually compact |
| Comments | Not in standard JSON | Supported | Supported |
| Strict schema options | Available through separate tools | Strong, mature schema ecosystem | Available through separate tools |
| Common use | REST APIs and application data | SOAP, enterprise and document exchange | DevOps and configuration |
| Main caution | Limited native value types | More syntax and complexity | Indentation and parser complexity |

There is no winner in every category. The correct format depends on the system's requirements.

---

## Topic 3.7 — A Practical Decision Guide

### Choose JSON When...

* Building a REST API for a web or mobile application.
* Exchanging ordinary objects and arrays.
* Working with browser clients.
* Prioritizing broad tooling support and simple payloads.

### Choose XML When...

* Integrating with an existing SOAP or XML-based system.
* Working with complex documents or namespaces.
* Following an industry standard that requires XML.
* Depending on a mature XML schema and transformation ecosystem.

### Choose YAML When...

* Writing configuration that humans will maintain.
* Defining CI/CD workflows or infrastructure manifests.
* Working with tools whose established format is YAML.
* Comments and low visual noise are important.

### Quick Examples

| If I am building... | Likely starting choice |
| --- | --- |
| REST API for a React application | JSON |
| Mobile backend response | JSON |
| SOAP integration with a bank | XML |
| Enterprise document exchange | XML |
| Docker Compose configuration | YAML |
| Kubernetes deployment manifest | YAML |
| GitHub Actions workflow | YAML |

The phrase **starting choice** matters. Real requirements can always change the decision.

---

## My Biggest Realization

I used to think newer and shorter automatically meant better.

JSON looked modern, XML looked old, and YAML looked clean. But that comparison ignored why each format exists.

Now I see the decision differently:

```text
JSON → Simple application data exchange
XML → Rich document structure and mature standards
YAML → Human-managed configuration
```

Good engineering is not choosing the most popular tool. It is understanding the problem well enough to choose the appropriate trade-off.

## Final Summary

**1. A serialization format defines how structured data is represented**

The same information can appear in JSON, XML, YAML, or another agreed format.

**2. Different formats optimize for different jobs**

No single format is best for APIs, documents, configuration, and high-performance communication at the same time.

**3. JSON is the common starting point for web APIs**

It is broadly supported, relatively concise, and maps naturally to application data.

**4. XML remains valuable in structured and long-lived systems**

Its schemas, namespaces, and document tooling solve needs that simple JSON payloads may not address.

**5. YAML is strongest when humans maintain configuration**

Its readable syntax is useful, but indentation and parser behavior require care.

### Checkpoint Questions

**Why isn't JSON the only serialization format?**

Because systems have different priorities, including readability, schemas, document structure, compatibility, tooling, and performance.

**Why is JSON common in web APIs?**

Browsers and backend languages support it broadly, and its objects and arrays fit common application data well.

**Why might an enterprise system choose XML?**

It may depend on SOAP, XML schemas, namespaces, document standards, or established integrations.

**Why is YAML common in DevOps?**

It gives people a relatively readable way to maintain structured configuration and automation files.

**Is one of these formats always best?**

No. The right choice depends on the actual requirements and ecosystem.
