# HTTP Methods Are the Vocabulary of an Express API

> *“The path identifies the resource; the HTTP method communicates what the client intends to do with it.”*

## 1. Introduction: The HTTP Verb as Intent

Part 3 showed that an Express route contains a method, path, and handler:

```js
router.get("/posts/:postId", getPost);
```

The path `/posts/:postId` identifies a resource shape. The method `GET` communicates the requested interaction. Changing only the method changes the meaning:

```text
GET    /posts/post_42 → retrieve the post
PUT    /posts/post_42 → replace the post
DELETE /posts/post_42 → remove the post
```

Day 3 introduced methods as part of routing. Day 9 examined their REST and HTTP semantics. Now I am connecting both ideas to Express code.

### Semantic HTTP

**Semantic HTTP** means using methods and status codes according to their shared meanings instead of treating HTTP as a tunnel for custom commands.

This design hides intent in paths:

```text
POST /getPost
POST /createPost
POST /replacePost
POST /deletePost
```

This design uses the vocabulary HTTP already provides:

```text
GET    /posts/:postId
POST   /posts
PUT    /posts/:postId
DELETE /posts/:postId
```

The benefits are not only visual. Clients, browsers, caches, proxies, documentation tools, and developers can reason from standard semantics.

Two properties are especially important:

| Property | Meaning |
| --- | --- |
| **Safe** | The client does not request a state change on the server |
| **Idempotent** | Repeating the same intended request has the same intended effect as making it once |

Safety does not mean that absolutely nothing happens. A GET request can create logs, metrics, or billing records as incidental effects. The client must not be asking GET to delete a post or send a payment.

Idempotency does not require identical responses. Repeating a DELETE might return `204` first and `404` later, while the intended final state—resource absent—remains the same.

Express provides `router.get()`, `router.post()`, `router.put()`, and `router.delete()`. It does not enforce their meanings. Semantic correctness remains my responsibility.

## 2. GET: The Safe Retriever

GET asks for a representation of a resource. It should retrieve data without requesting a state change.

```js
router.get("/", listPosts);
router.get("/:postId", getPost);
```

### Collection and Member Retrieval

A controller for one post might be:

```js
export async function getPost(req, res) {
  const post = await postsService.getById(req.params.postId);

  if (!post) {
    return res.status(404).json({ error: "Post not found" });
  }

  return res.status(200).json({ data: post });
}
```

The path parameter identifies the member:

```text
GET /posts/post_42
                 ↑ which post?
```

A collection route uses query strings to shape the returned view:

```js
export async function listPosts(req, res) {
  const page = Number(req.query.page ?? 1);
  const status = req.query.status;

  if (!Number.isSafeInteger(page) || page < 1) {
    return res.status(400).json({
      error: "page must be a positive integer",
    });
  }

  const result = await postsService.list({ page, status });
  return res.status(200).json(result);
}
```

```text
GET /posts?status=published&page=2
           ↑ filter             ↑ collection window
```

The distinction remains:

```text
Path parameter → identifies the resource
Query string   → filters, sorts, searches, or paginates its representation
```

Both sources contain untrusted strings and require validation.

### GET Is Safe and Idempotent

These requests should not publish or delete anything:

```text
GET /posts/post_42
GET /posts/post_42
GET /posts/post_42
```

The representation can change between requests because another actor edited the post, but repeating GET does not itself request that change.

This safety allows browsers and automated systems to follow links or prefetch resources without expecting destructive behavior. A route such as this violates that expectation:

```js
// Incorrect: GET requests a state change
router.get("/:postId/delete", deletePost);
```

Use DELETE with authentication and authorization instead.

### GET and Caching

GET responses can participate in HTTP caching. The server can provide freshness rules and validators:

```http
Cache-Control: public, max-age=60
ETag: "post_42-v7"
```

A cache may reuse a fresh response or revalidate a stale one. Express can generate ETags, but the application still needs an intentional cache policy, especially for private data.

GET does not mean “always cached.” Authorization, `Cache-Control`, cookies, query variants, and intermediary configuration affect whether reuse is safe.

## 3. POST: The Creator

POST sends data to a resource for processing. In a resource-oriented API, it commonly creates a new member inside a collection:

```text
POST /posts
```

The server, rather than the client, usually assigns the new member's identifier.

### Why `express.json()` Is Required

An HTTP request body arrives as bytes. Express does not assume every body is JSON or parse it automatically without matching middleware.

```js
const app = express();

app.use(express.json({ limit: "100kb" }));
app.use("/api/v1/posts", postsRouter);
```

`express.json()` checks requests with matching JSON content types, reads the body stream, parses the JSON, and populates `req.body`. It must be registered before routes that need the body.

Without it, `req.body` is `undefined` in Express 5 for an unparsed body.

Parsing is not validation. This remains client-controlled input:

```js
export async function createPost(req, res) {
  const { title, body } = req.body ?? {};

  if (typeof title !== "string" || typeof body !== "string") {
    return res.status(400).json({
      error: "title and body must be strings",
    });
  }

  const post = await postsService.create({
    title,
    body,
    authorId: req.user.id,
  });

  return res
    .status(201)
    .location(`/api/v1/posts/${post.id}`)
    .json({ data: post });
}
```

### `201 Created` and `Location`

`201 Created` communicates that the request resulted in one or more new resources. When the primary resource has its own URI, the response should identify it—commonly with `Location`:

```http
HTTP/1.1 201 Created
Location: /api/v1/posts/post_42
Content-Type: application/json

{
  "data": {
    "id": "post_42",
    "title": "Express Methods"
  }
}
```

Returning `200` would be understandable to many clients, but `201` states the outcome more precisely.

### POST Is Not Inherently Idempotent

If the client sends the same creation request twice:

```text
POST /posts → creates post_42
POST /posts → might create post_43
```

The method itself does not promise idempotency. This matters when a response is lost: the client might not know whether the server committed the creation.

For operations where duplication is costly, an API can add an idempotency-key contract. That is application policy layered on POST; it does not make POST idempotent by default.

POST is also broader than creation. It can model processing or domain actions, but the API should document the target resource and outcome clearly.

## 4. PUT: The Full Replacement

PUT asks the server to create or replace the state of the resource at the target URI. The client knows the target:

```text
PUT /posts/post_42
```

A replacement representation should contain the complete replaceable state required by the contract:

```json
{
  "title": "Express HTTP Methods",
  "body": "A complete replacement body.",
  "status": "published"
}
```

### Express Implementation

```js
router.put("/:postId", replacePost);
```

```js
export async function replacePost(req, res) {
  const { title, body, status } = req.body ?? {};

  if (
    typeof title !== "string" ||
    typeof body !== "string" ||
    !["draft", "published"].includes(status)
  ) {
    return res.status(400).json({
      error: "A complete valid post representation is required",
    });
  }

  const post = await postsService.replace(req.params.postId, {
    title,
    body,
    status,
  });

  if (!post) {
    return res.status(404).json({ error: "Post not found" });
  }

  return res.status(200).json({ data: post });
}
```

This API chooses replacement of an existing post only. Another valid contract could allow PUT to create the client-selected URI when it does not exist, returning `201 Created`. The behavior must be documented consistently.

### Why PUT Is Idempotent

Suppose the current resource is:

```json
{ "title": "Old", "body": "Old", "status": "draft" }
```

The client sends the same complete replacement twice:

```text
PUT replacement → resource becomes representation X
PUT replacement → resource remains representation X
```

The final intended state is the same. Logs and update timestamps might still change as incidental effects, but the requested resource state does not accumulate another result each time.

Idempotency makes retrying after uncertain transport failure safer. It does not solve concurrent updates automatically; conditional requests with validators may still be needed to prevent lost updates.

### PUT Versus POST Versus PATCH

| Method | Target and intent |
| --- | --- |
| `POST /posts` | Process data under the collection, commonly creating a server-identified member |
| `PUT /posts/:id` | Completely replace or create the state at a known target URI according to the contract |
| `PATCH /posts/:id` | Apply a partial modification document |

If the client sends only `{ "title": "New" }`, calling it PUT while silently preserving every omitted field makes PUT behave like an undocumented PATCH. The contract should make replacement versus partial modification explicit.

## 5. DELETE: The Remover

DELETE asks the server to remove the association between the target URI and its current functionality:

```js
router.delete("/:postId", authenticate, authorizeDelete, deletePost);
```

```js
export async function deletePost(req, res) {
  const removed = await postsService.remove(req.params.postId);

  if (!removed) {
    return res.status(404).json({ error: "Post not found" });
  }

  return res.status(204).send();
}
```

### DELETE Is Idempotent

The intended effect is “the target resource is absent”:

```text
First DELETE  → resource becomes absent
Second DELETE → resource remains absent
```

The second request can return `404` because no current resource was found. Idempotency concerns the intended effect, not identical response bodies or status codes.

### `204 No Content` Versus `200 OK`

Use `204 No Content` when deletion has completed and there is no response representation to send:

```js
return res.status(204).send();
```

A `204` response must not contain a message body. Code such as `res.status(204).json(...)` expresses conflicting intentions.

Use `200 OK` when returning useful confirmation or a representation describing the outcome:

```js
return res.status(200).json({
  data: { id: postId, deleted: true },
});
```

If deletion is accepted for asynchronous processing rather than completed, `202 Accepted` can be more accurate, though that is outside this part's core status set.

### Security Considerations

DELETE is destructive, so matching the route is only the first step. The server should:

- authenticate the caller;
- authorize deletion of this specific resource;
- validate the identifier;
- protect cookie-authenticated requests against CSRF where applicable;
- preserve audit information when required;
- define cascade, retention, and soft-delete behavior;
- avoid revealing sensitive existence details across authorization boundaries.

Idempotent does not mean harmless. DELETE is idempotent but not safe.

## 6. Status Codes: Summarizing the Outcome

The method communicates request intent. The status code summarizes what happened.

| Status | Meaning in this posts API |
| --- | --- |
| `200 OK` | Retrieval or mutation succeeded and a representation is returned |
| `201 Created` | A new resource was created |
| `204 No Content` | The operation succeeded with no response body |
| `400 Bad Request` | Request input is malformed or violates the public input contract |
| `404 Not Found` | No current resource matches the target URI, or it is intentionally concealed |

### Choosing Between Them

```text
GET /posts/post_42 found          → 200 + post representation
POST /posts created post_43       → 201 + Location + representation
PUT /posts/post_42 replaced       → 200 + representation, or 204 without one
DELETE /posts/post_42 completed   → 204 without a body
Invalid page or malformed fields  → 400
Validly shaped missing post ID    → 404
```

`400` and `404` answer different questions:

```text
400 → “I cannot accept this request input.”
404 → “The target resource is not available.”
```

An invalid identifier format such as `/posts/%%%` may be rejected as `400`. A valid identifier such as `post_999` that has no corresponding resource is `404`.

Status codes communicate broad categories. A consistent JSON error body can provide stable application details:

```json
{
  "error": {
    "code": "POST_NOT_FOUND",
    "message": "Post not found"
  }
}
```

## Checkpoints

### Why is GET both safe and idempotent?

The client requests retrieval, not a state change, and repeating that retrieval does not request accumulating effects. The returned representation may still change as the resource changes independently.

### Why can repeating POST create duplicates?

POST does not promise idempotency. Repeating the same creation request can ask the collection to process it again and create another member unless the API adds a deduplication contract.

### What makes PUT different from PATCH?

PUT represents complete replacement at the target URI, while PATCH applies a partial modification. An API should not call an update PUT while treating omitted fields as “leave unchanged” without explicitly defining nonstandard semantics.

### Why can repeated DELETE return different statuses and remain idempotent?

The first request can delete the resource and return `204`; the second can find nothing and return `404`. The intended final resource state is absent after both.

### When should I use `201` instead of `200`?

Use `201 Created` when the request created a new resource, usually with a `Location` header identifying its URI. Use `200 OK` for a successful operation that returns a representation without specifically communicating creation.

## What I Learned in Part 5

Express method functions are small, but their HTTP meanings are larger:

```text
GET retrieves safely and idempotently.
POST processes data and commonly creates a new resource.
PUT replaces a known target and is idempotent.
DELETE removes a target, is idempotent, but is not safe.
Status codes summarize the actual outcome.
```

> **A well-designed Express API does not merely match methods—it preserves the shared semantics that allow clients and infrastructure to predict its behavior.**
